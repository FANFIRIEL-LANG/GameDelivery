Версия immutable, но нет effective_from/effective_to и нет контракта, что created_at равен моменту вступления внешнего объявления в силу.
- BrowserSalesReader запрашивает id, status, createdAt. PlayerokAdapter._map_deal() переносит createdAt в created_at; отдельного paid_at/paidAt, времени смены статуса или истории переходов в PAID нет. Локальные created_at у gd_deals/orders и baseline_completed_at/last_sync_at — время записи/синхронизации GameDelivery, не оплаты Playerok.
- Поэтому сейчас сопоставить PAID с ConfigVersion по времени достоверно нельзя. Даже если внешнее createdAt означает дату создания сделки, оно не является доказанным временем оплаты.

### Выбор и защита версии

- Для сделки без уже созданного заказа sync._listing_config() выбирает максимальный version_number. _upsert_deal() может обновлять config_version_id при повторной синхронизации до создания Order. resolve_unresolved_deal() также выбирает последнюю версию.
- Например, сделка оплачена при v1, затем сохранена v2, а первый sync случился позже: заказ и строки будут созданы из v2. Это возможно, потому что нет payment timestamp и исторического interval matching.
- После создания Order версия сохраняется: _upsert_deal() берёт старый config_version_id, ConfigVersion immutable, Order INSERT OR IGNORE; строки материализуются только при первом создании Order. Следовательно, риск относится к первому pin, а не к обычному повторному sync уже существующего заказа.

### Рекомендуемый fail-closed контракт

Не назначать latest PAID-сделке, если версия на момент оплаты не доказана. Сохранить Deal без Order/OrderLines и без исполнения, пока не появится подтверждённый payment timestamp плюс однозначный интервал действия версии либо оператор явно не выберет точный существующий config_version_id с аудитом. Повторная синхронизация не должна переписывать уже закреплённую версию. Переиспользовать существующие ConfigVersion; не вводить отдельную систему версий. Имеющийся ConfigVersion.created_at можно считать effective_from только после отдельного утверждения семантики и проверки timestamp границ/точности; это не подтверждено текущим кодом.

Текущая gd_deals schema позволяет config_version_id NULL, включая listing-resolved row, но код не использует это для неопределённой версии. Потребуется явная трактовка статуса конфигурации, так как listing_resolution_status описывает сопоставление объявления, не достоверность версии.
