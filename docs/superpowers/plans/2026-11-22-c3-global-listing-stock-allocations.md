# Stage C.3 — общий склад ASF и количественные аллокации объявлений

Дата: 2026-11-22  
Ветка: `work/local-sync`  
Статус: архитектурное решение для реализации; production-код не менялся.

## 1. Решение по пользовательской модели

GameDelivery показывает все подключённые ASF-боты как **единый общий склад**. Пользователь не выбирает бота при настройке объявления и задаёт только количество единиц на одну покупку.

Программа автоматически закрепляет за объявлением точное количество единиц из совокупного инвентаря всех допущенных ботов. Закрепление сохраняет физическое местоположение каждой части: `bot_name`, `asset_id`, игру/app/context и `units`. Эти поля нужны для исполнения и аудита, но не являются пользовательской настройкой.

Пример: общий запас 100 units распределён между тремя ботами. Объявления A/B/C запрашивают 3/5/10 units. GameDelivery выделяет ровно 18 units, свободный остаток равен 82. Один стек Asset ID с Amount=100 может быть разделён на несколько allocation rows, если сумма всех активных выделений этого физического стека не превышает подтверждённый Amount.

## 2. Термины и инварианты

- **Общий склад** — объединение актуальных инвентарей всех разрешённых и подключённых ASF-ботов. Это логический пул, а не перенос предметов между ботами.
- **Физический ресурс** — ключ `(game_id, app_id, context_id, bot_name, asset_id)`. Asset ID без bot_name недостаточен для идентификации владельца.
- **Stock observation** — последнее проверенное количество физического ресурса и признаки его доступности/свежести.
- **Listing allocation** — конкретные units физического ресурса, закреплённые за listing generation.
- **Order allocation** — units, атомарно переведённые из listing allocation в обязательство конкретной OrderLine.
- **Free stock** — подтверждённые доступные units за вычетом всех активных listing allocations, order allocations и блокирующих/неопределённых резервов.

Обязательные инварианты:

1. Пользователь не выбирает ASF-бота; подбор выполняется автоматически по общему пулу.
2. Каждая allocation хранит физического владельца (бота), Asset ID и положительное целое количество units.
3. Для одного физического ресурса сумма всех блокирующих allocation units не превышает последнее подтверждённое фактическое Amount.
4. Одни и те же units не могут одновременно принадлежать двум объявлениям или объявлению и заказу.
5. Выделение для объявления выполняется целиком: ровно N или отказ без частичной аллокации.
6. Перевод listing allocation в order allocation выполняется одной транзакцией; повторное событие оплаты идемпотентно.
7. Активный, отправляемый или имеющий UNKNOWN outcome заказ не теряет закреплённые units и не возвращает их в свободный пул.
8. Уменьшение/удаление/отключение объявления освобождает только не переданные заказам units. Уже зарезервированные за заказами units не отбираются.
9. Устаревший snapshot, неизвестная tradable-состояние, конфликт Asset ID или нехватка общего количества блокируют allocation/dispatch fail-closed.
10. При нехватке хотя бы одной единицы не создавать частичное предложение и не отправлять часть обязательного заказа.

## 3. Автоматическое распределение по ботам

Аллокатор получает требуемое количество N и selector товара, затем строит кандидатов из свежих инвентарей всех разрешённых ботов. Кандидат должен точно совпадать по game/app/context и идентичности предмета, быть доступным и иметь подтверждённую tradable-семантику для соответствующего handler.

Аллокатор вычисляет свободные units каждого физического ресурса как подтверждённый Amount минус сумма всех блокирующих allocations. Затем выбирает набор ресурсов, покрывающий N, и сохраняет конкретные slices. Стратегия выбора должна быть детерминированной (например, стабильная сортировка по bot_name и asset_id после фильтрации), чтобы повторяемые входы давали воспроизводимый план. При этом выбор не должен ухудшать возможность доставки: ограничения игры/handler и торговые лимиты учитываются до фиксации allocations.

Если общий свободный запас меньше N, операция полностью отклоняется и возвращает точную нехватку. Никакая частичная allocation не остаётся в базе.

## 4. Покупка: listing → order

Для оплаченной сделки используется listing ID + generation/config version как ключ конфигурации. В одной `BEGIN IMMEDIATE` транзакции:

1. Проверить idempotency key события сделки и отсутствие уже созданного обязательства.
2. Загрузить все активные allocations текущего listing generation.
3. Проверить, что их суммарные units полностью покрывают quantity заказа.
4. Перевести ровно требуемые slices из listing ownership в order ownership, сохранив bot/asset/units и ссылку на OrderLine.
5. Если allocation объявления больше одного заказа по времени не допускает повторного использования одних units, уменьшить остаток listing allocation на переданное количество; остаток остаётся у объявления.
6. Зафиксировать order lines, delivery manifests и события ledger в той же транзакционной границе либо обеспечить эквивалентную атомарность через уже существующий caller transaction.

Дубликат paid event не создаёт повторную OrderLine и не перемещает units повторно. Изменение текущей конфигурации объявления не меняет snapshot уже созданной сделки.

## 5. Несколько ботов и исполнение

Общий склад не означает, что физические предметы становятся взаимозаменяемыми между аккаунтами: каждый Asset остаётся на конкретном боте. План доставки может содержать slices нескольких ботов и раскладываться на соответствующие DeliveryLegs.

До первого внешнего send необходимо проверить весь обязательный manifest целиком: каждый bot/asset, точный units, свежий inventory, app/context, item identity, tradable и отсутствие конфликтующих резервов. Если любой slice не подтверждён, не отправлять ни одну часть заказа.

Если конкретный ASF handler не поддерживает безопасную много-ботовую/много-leg доставку или точную отправку частичного стека, этот заказ блокируется до реализации и тестирования такого handler. Нельзя молча выбрать один бот, отправить только доступную часть или подобрать похожий предмет.

Если одна leg уже ушла во внешний Steam offer, а другая leg завершилась ошибкой/UNKNOWN, первая не откатывается. Сохраняется частичный/неопределённый outcome; незавершённые allocations остаются заблокированными до reconciliation/operator action.

## 6. Изменение, выключение и удаление объявления

Операции изменения количества и отключения применяются к конкретному listing generation.

- Увеличение количества: выделить недостающие units из общего свободного пула атомарно; при нехватке оставить прежнюю конфигурацию и allocation без изменений.
- Уменьшение количества: освободить только незадействованный listing остаток. Units, уже переданные в OrderLine или находящиеся в active/pending/UNKNOWN delivery, не трогать.
- Отключение/удаление: прекратить новые продажи/поколения и освободить только listing-owned остаток после проверки отсутствия незавершённого перехода; order-owned units продолжают жить по жизненному циклу заказа.
- Перераспределение между ботами: разрешено только через атомарную операцию release + allocate для свободных listing-owned units после свежей проверки обоих физических ресурсов. Нельзя менять bot/asset у активной order allocation.

## 7. Изменения схемы БД — обязательные требования, не готовая миграция

Текущая `gd_resource_reservations` содержит `units`, `owner_type='listing'` и `listing_generation`, но уникальный индекс `idx_gd_resource_active_global` запрещает несколько активных строк на один `(bot_name, asset_id)`. Триггеры canonical reservation также блокируют вторую активную строку по нормализованному asset key. Поэтому текущая схема не может выразить разделение одного стека между объявлениями.

До реализации требуется отдельный migration design, который:

- сохраняет физическую уникальность и нормализацию Asset ID;
- вводит канонический учёт observed stock Amount на физический ресурс (или другой доказуемый источник агрегатного лимита);
- разрешает несколько quantity allocations на один физический стек только при соблюдении агрегатного лимита;
- атомарно защищает `SUM(blocking allocation units) <= observed Amount` при конкурентных writers;
- сохраняет глобальную защиту от дублей и alias-конфликтов;
- учитывает состояния active, pending/unknown, released и consumed без преждевременного освобождения;
- сохраняет legacy `steam_asset_reservations` только как совместимую проекцию там, где её уникальная модель это допускает; она не должна быть источником истины для quantity stock;
- проходит backup/rollback, foreign_key_check, legacy conflict preservation и migration tests на копиях существующих БД.

Не удалять текущие уникальные индексы/триггеры точечно до готовности полного migration path и тестов совместимости.

## 8. Тесты при реализации

Обязательный набор:

- 100 units на одном stack Asset ID; allocations 3, 5, 10; занято 18, свободно 82.
- Один стек распределён между несколькими listing generations без превышения Amount.
- Три бота с одним товаром: allocation 10 корректно распределена по нескольким ботам; UI/API не требует выбора бота.
- Нехватка на 1 unit приводит к полному отказу без частичных строк.
- Два конкурентных listing allocations не могут зарезервировать одни units.
- Два конкурентных paid events не могут дважды перевести одну allocation в order.
- Повторный paid event идемпотентен.
- Уменьшение/отключение listing не освобождает units активного заказа.
- UNKNOWN/pending offer удерживает units; release запрещён без доказанного terminal outcome.
- Уменьшение фактического Amount ниже суммы allocations создаёт inventory conflict и блокирует новые операции, а не обрезает allocations автоматически.
- Смена bot inventory/удаление asset не приводит к автоматическому переприсвоению order-owned units.
- Multi-bot manifest проходит preflight целиком; при ошибке одного slice ни одна leg не отправляется.
- Старые миграции, legacy projection, normalized asset aliases и восстановление после rollback остаются корректными.

## 9. Границы

На этом этапе не реализуются UI, Playerok browser automation, автоматическое создание/публикация объявлений, auto-relist и реальные Steam offers. Не меняется лицензионная система. Не используется Steam Web API key. Все Steam inventory/send операции остаются через ASF. Реальные трейды запрещены в рамках разработки и тестирования.

Первый implementation slice после утверждения дизайна: migration + stock observation contract + unit tests на aggregate allocation. Затем сервис listing allocation/transfer и конкурентные тесты. Только после этого — интеграция quantity-aware delivery manifest/ASF handler.
