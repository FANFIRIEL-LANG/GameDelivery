## 1. Назначение и границы

Этап C расширяет существующий GameDelivery до общей системы контроля права на выдачу и нескольких независимых способов доставки.

Обязательные категории:
- Steam Trading Cards — сохранить существующий рабочий путь.
- Предметы из игр, в том числе CS2 и будущие игровые модули.
- Цифровые ключи, коды и лицензии.
- Файлы.
- Услуги.

Обязательное правило количества:

`remaining_to_fulfill = promised_item_quantity - reserved_item_quantity - delivered_item_quantity`

Для Playerok количество выдаваемых игровых предметов задаётся в конфигурации конкретного объявления: `delivery_quantity_per_deal`. Подтверждённая покупка этого объявления создаёт обязательство на указанное количество; денежная сумма сделки не является количеством товара. Если площадка отдельно предоставляет фактическое количество покупаемых единиц, оно учитывается отдельным полем и не подменяет настройку количества предметов на одну покупку. Для каждого заказа сохраняется неизменяемый снимок версии конфигурации объявления.

**Этап C — отдельный план расширения, а не замена исторического плана 0–9.** Он связан с существующими этапами 5 (инвентарь/резервации), 6 (заказы/Playerok) и 7 (Steam delivery). Их текущие статусы и незавершённые ручные проверки не меняются этим документом. Этапы 8–9 и их release gates сохраняются; после внедрения C их проверки потребуется повторить на итоговом кандидате.

Не менять `main`, не менять base PR #4, не сливать PR. Все работы — только в `feature/asf-bulk-account-import`. Каждый блок выполняется отдельно; к следующему блоку переходить после подтверждения пользователя.

### Не входит в этап C

- Переписывание приложения или замена PySide6/SQLite.
- Прямые Steam Web API для работы с аккаунтами, инвентарём и трейдами: Steam-интеграция остаётся через ASF.
- Автоматическое принятие входящих Steam-обменов.
- Автоматический повтор отправки при неизвестном результате.
- Полноценный браузерный движок, полный редактор сценариев и общий набор операций управления объявлениями/сообщениями Playerok остаются отдельным связанным направлением. В этапе C фиксируются необходимые контракты: идентификаторы сделок/чатов, привязка объявления к конфигурации выдачи и точки интеграции; браузерная автоматизация включается только после отдельной проверки.
- Объявление любой операции автоматической, пока реальный интерфейс площадки или ASF не проверен.

### 2.1 Ограничение данных Playerok и новая настройка количества

На проверенном кодовом baseline Playerok query читает сделки в статусах `PAID` и `SENT`, но не извлекает отдельное количество единиц. `source_amount` в `delivery_orders` — денежная сумма, не количество.

Пользователь уточнил целевую бизнес-логику: количество игровых предметов на одну покупку задаётся внутри GameDelivery отдельно для каждого объявления. Поэтому:
- `source_amount` никогда не используется как количество;
- для объявления хранится `delivery_quantity_per_deal` и правило выбора допустимых предметов;
- факт оплаты/новой сделки подтверждается данными Playerok, а количество предметов для выдачи берётся из сохранённой конфигурации объявления;
- изменение настройки объявления влияет только на будущие сделки; существующий заказ хранит снимок конфигурации, действовавший при его обнаружении/подтверждении;
- точное извлечение ID объявления и сделки из текущего браузерного интерфейса требует live-проверки в отдельном браузерном этапе.

### 2.2 Хранилища, которые нельзя ломать

На текущей ветке обнаружены разные таблицы и хранилища с разными назначениями:
- `orders` — базовая очередь `core/orders`;
- `delivery_orders` и `delivery_order_assets` — рабочий UI-поток заказов/активов;
- `steam_asset_reservations` — резервации конкретных Steam asset ID;
- `steam_inventory_snapshot` и `steam_inventory_snapshot_meta` — снимки Steam-карточек;
- `game_inventory_snapshot` и `game_inventory_snapshot_meta` — отдельные снимки игровых инвентарей;
- `sent_offers.json` в локальном хранилище ASF-плагина — идемпотентность и результаты Steam trade.

Сначала нужно установить фактическое использование каждой модели и их связи. Нельзя удалять или сливать таблицы до проверки миграции и сохранности существующих заказов/резервов.

## 3. Инварианты будущей системы

1. **Подтверждённая оплата.** `paid_quantity` поступает из проверенного источника заказа/платежа или из явно подтверждённой оператором корректировки с обязательной причиной. Цена/сумма не является количеством.
2. **Единица учёта — строка заказа.** Для заказа с несколькими товарами количество считается по каждой строке отдельно; нельзя смешивать количество карточек, предметов, ключей, файлов и услуг.
3. **Единый остаток.** Доступное количество вычисляется из подтверждённого оплаченного количества, активных резервов и уже совершённых выдач. Формула должна быть защищена атомарной транзакцией SQLite.
4. **Резерв до выдачи.** Нельзя выполнить обработчик без успешной резервации соответствующего количества/ресурса.
5. **Уникальные ресурсы.** Для Steam/игрового инвентаря и уникальных ключей резервируется конкретный ID/код. Один ресурс не может числиться активным резервом для двух заказов.
6. **Идемпотентность.** Повторное получение одного заказа/события/команды не создаёт второй резерв и не выдаёт товар второй раз.
7. **Неизвестный исход — блокировка.** Timeout, обрыв соединения или падение процесса после внешнего действия не трактуется как обычная ошибка. Автоматический повтор запрещён до сверки.
8. **Разделение состояний.** Подготовлено, зарезервировано, отправлено/передано, подтверждено получателем, завершено, отменено и неизвестный исход — не одно и то же состояние.
9. **Атомарное завершение.** Перенос единиц из резерва в завершённую выдачу выполняется один раз и фиксируется в аудите.
10. **Изоляция заказов.** Ошибка одного заказа не останавливает очередь; ошибки и повторы учитываются для конкретного заказа/строки/попытки.
11. **Аудит.** Резерв, освобождение, выдача, корректировка количества, ручное подтверждение и сверка имеют время, локальную ссылку на оператора/операцию и причину.
12. **Безопасность.** Ключи, токены, trade URL token, cookies и другие секреты не попадают в Git, логи, тестовые дампы или сообщения об ошибке.

### C.2 — Доменная модель объявлений, количества и правил подтверждения

**Цель:** согласовать точную семантику объявления, обязательства по количеству предметов, общего инвентаря, резерва, многоэтапной выдачи и подтверждений.

**Работы:**
- Определить сущности marketplace listing, версию конфигурации объявления, заказ и строки заказа. Категория товара и способ доставки остаются независимыми параметрами.
- Для каждого объявления задать `delivery_quantity_per_deal` — сколько предметов/единиц GameDelivery должен выдать за одну подтверждённую покупку этого объявления.
- Разрешить привязку одного или нескольких конкретных типов/селекторов предметов к одному объявлению, а одного типа предмета — к нескольким объявлениям. Селектор должен идентифицировать товар по игре/app/context и устойчивым характеристикам, а выдача — по точному уникальному asset ID.
- Сохранять в заказе неизменяемый снимок версии конфигурации: listing ID, название/ссылка, требуемое количество, список разрешённых селекторов предметов, разрешённые боты и правила распределения. Изменение объявления применяется только к новым сделкам.
- Разделить внешний ID сделки (`deal_id`) и ID чата (`chat_id`). По предоставленным скриншотам URL детальной сделки имеет вид `/deal/<UUID>`, а URL чата — `/chats/<UUID>`; это разные идентификаторы и разные сущности. При реализации нужно подтвердить стабильность этих идентификаторов на живом интерфейсе.
- Определить безопасное обнаружение новых сделок: вести постоянный реестр ранее увиденных `deal_id` с уникальностью в рамках marketplace account; `chat_id` хранить как контекст/маршрут общения, но не как ключ заказа.
- При первом подключении выполнить baseline-сверку существующих сделок: уже найденные deal ID пометить как исторически известные, не запускать автоматическую выдачу по ним. Автоматическое обнаружение новых заказов включать только после завершённой сверки; при неполной пагинации/ошибке baseline состояние остаётся `baseline_incomplete`, а автодействие блокируется до проверки оператором.
- После baseline новый заказ-кандидат создаётся только при появлении ранее неизвестного `deal_id` и проверенном статусе оплаты. Изменение unread-счётчика, появление нового сообщения, новый чат, обновление старой сделки или повторное отображение карточки сами по себе не создают заказ.
- Повторные сканирования, изменение сортировки/порядка чатов, обновление страницы и повторная доставка событий должны быть идемпотентными. Если deal ID невозможно прочитать или связать с карточкой сделки — не угадывать по покупателю/чату; поместить запись в ручную сверку.
- Определить общий логический пул инвентаря всех разрешённых ботов. Один и тот же физический asset ID может быть назначен нескольким объявлениям как допустимый источник, но может быть зарезервирован только один раз на всю систему.
- Определить распределение заказа по нескольким ботам и нескольким Steam-трейдам/legs: один родительский заказ может состоять из нескольких независимых отправок с точным списком asset ID и собственным состоянием каждой отправки.

**Работы:**

- Выбирать обработчик по категории/типу товара и способу доставки, а не по названию товара.
- Поддержать родительский заказ с несколькими delivery legs, в том числе распределёнными по разным ботам и отдельным Steam-трейдам; каждая leg хранит собственные bot, exact asset IDs, idempotency key, offer ID и статус.
- Хранить попытки и результаты отдельно для заказа и каждой leg; частичный успех не маскировать статусом общей ошибки или полного успеха.
- Реализовать изоляцию ошибок по заказу и безопасное восстановление после перезапуска.
- Определить политику retry только для однозначно не выполненных операций; unknown всегда требует reconcile, а завершённые legs никогда не повторяются.
- Поддержать ручное подтверждение перед необратимым внешним действием и общий статус родительского заказа, вычисляемый из обязательных legs.

**Критерии приёмки:**
- Новый handler подключается без изменения логики остальных обработчиков.
- Ошибка одного заказа не блокирует следующий.
- Повторная команда с тем же idempotency key не запускает внешнее действие повторно.
- Unknown outcome блокирует автоматическую выдачу/повтор и отображает понятный статус.
- Contract tests проверяют все обязательные методы handler.

## 5. Решения, которые должны быть зафиксированы до реализации соответствующих блоков

1. **Связь Playerok deal/listing/chat.** Скриншоты показывают UUID в пути `/deal/<UUID>` и отдельный UUID в `/chats/<UUID>`. В браузерном этапе нужно проверить, что deal UUID стабилен и однозначно принадлежит сделке, а listing ID можно надёжно получить из карточки/страницы сделки. При невозможности получить точный ID автодоставка блокируется.
2. **Первичная синхронизация Playerok.** Предлагаемый безопасный default: все найденные при первичном baseline deal ID записываются как уже известные без автоматической выдачи; импорт старых неоплаченных/неисполненных сделок выполняется отдельным явным действием. Требуется проверить полноту обхода чатов/пагинации и определить ручной сценарий восстановления незавершённого baseline.
3. **Количество на одну покупку.** Пользователь задаёт `delivery_quantity_per_deal` в версии конфигурации объявления. Если площадка в будущем отдаёт собственное число покупаемых единиц, определить как оно умножает/согласуется с настройкой на одну покупку; до подтверждения не выводить это из суммы сделки.
4. **Момент учёта Steam delivery.** Разделять созданный offer, подтверждение ASF/mobile и принятие получателем. Точное условие перехода в delivered и момент освобождения резерва определить с учётом нескольких delivery legs.
5. **Частичная отправка на несколько ботов.** Рекомендуемое безопасное правило: до первой внешней отправки зарезервировать полный требуемый состав со всех выбранных ботов. Если полный состав собрать нельзя — не начинать отправку автоматически. Если одна из уже начатых legs завершилась неизвестно или другая не удалась после успешной отправки первой, сохранять частичный/unknown статус и сверять только незавершённые legs; успешные не повторять.
6. **Telegram proxy/действия.** Выбрать и проверить поддерживаемые схемы proxy на реальном сетевом клиенте; подтвердить, какие команды/ответы можно безопасно выполнять через Bot API и проверенный Playerok browser/adapter path. Токен хранить только в системном хранилище.
7. **Файлы и прочие площадки.** Автоматическая передача возможна только после проверки реальной возможности конкретной площадки. Само наличие файла не считается доставкой.

Эти решения должны быть закрыты в соответствующем блоке до изменения схемы/кода.

## 6. Метод работы по каждому блоку

1. Перед началом повторно проверить HEAD ветки, PR, нужные файлы, тесты и текущее состояние CI.
2. Кратко зафиксировать цель, разрешённую область файлов и критерии приёмки.
3. Изучить текущие реализации до внесения изменений.
4. Для кода применять TDD: добавить тест, увидеть ожидаемое падение, внести минимальное исправление, прогнать целевые и регрессионные тесты.
5. Проверить полный CI на получившемся SHA, если изменения затрагивают соответствующие workflows.
6. Обновить мастер-журнал и этот план только по фактически подтверждённым результатам.
7. Остановиться на границе блока и ждать разрешения пользователя на следующий блок.
