## 1. Назначение и границы

Этап C расширяет существующий GameDelivery до общей системы контроля права на выдачу и нескольких независимых способов доставки.

Обязательные категории:
- Steam Trading Cards — сохранить существующий рабочий путь.
- Предметы из игр, в том числе CS2 и будущие игровые модули.
- Цифровые ключи, коды и лицензии.
- Файлы.
- Услуги.

Обязательное правило количества:

`remaining_to_fulfill = promised_item_quantity - reserved_item_quantity - delivered_item_quantity`

Для Playerok количество выдаваемых игровых предметов задаётся в конфигурации конкретного объявления: `delivery_quantity_per_deal`. Подтверждённая покупка этого объявления создаёт обязательство на указанное количество; денежная сумма сделки не является количеством товара. Если площадка отдельно предоставляет фактическое количество покупаемых единиц, оно учитывается отдельным полем и не подменяет настройку количества предметов на одну покупку. Для каждого заказа сохраняется неизменяемый снимок версии конфигурации объявления.

**Этап C — отдельный план расширения, а не замена исторического плана 0–9.** Он связан с существующими этапами 5 (инвентарь/резервации), 6 (заказы/Playerok) и 7 (Steam delivery). Их текущие статусы и незавершённые ручные проверки не меняются этим документом. Этапы 8–9 и их release gates сохраняются; после внедрения C их проверки потребуется повторить на итоговом кандидате.

Не менять `main`, не менять base PR #4, не сливать PR. Все работы — только в `feature/asf-bulk-account-import`. Каждый блок выполняется отдельно; к следующему блоку переходить после подтверждения пользователя.

### Не входит в этап C

- Переписывание приложения или замена PySide6/SQLite.
- Прямые Steam Web API для работы с аккаунтами, инвентарём и трейдами: Steam-интеграция остаётся через ASF.
- Автоматическое принятие входящих Steam-обменов.
- Автоматический повтор отправки при неизвестном результате.
- Полноценный браузерный движок, полный редактор сценариев и общий набор операций управления объявлениями/сообщениями Playerok остаются отдельным связанным направлением. В этапе C фиксируются необходимые контракты: идентификаторы сделок/чатов, привязка объявления к конфигурации выдачи и точки интеграции; браузерная автоматизация включается только после отдельной проверки.
- Объявление любой операции автоматической, пока реальный интерфейс площадки или ASF не проверен.

### 2.1 Ограничение данных Playerok и новая настройка количества

На проверенном кодовом baseline Playerok query читает сделки в статусах `PAID` и `SENT`, но не извлекает отдельное количество единиц. `source_amount` в `delivery_orders` — денежная сумма, не количество.

Пользователь уточнил целевую бизнес-логику: количество игровых предметов на одну покупку задаётся внутри GameDelivery отдельно для каждого объявления. Поэтому:
- `source_amount` никогда не используется как количество;
- для объявления хранится `delivery_quantity_per_deal` и правило выбора допустимых предметов;
- факт оплаты/новой сделки подтверждается данными Playerok, а количество предметов для выдачи берётся из сохранённой конфигурации объявления;
- изменение настройки объявления влияет только на будущие сделки; существующий заказ хранит снимок конфигурации, действовавший при его обнаружении/подтверждении;
- точное извлечение ID объявления и сделки из текущего браузерного интерфейса требует live-проверки в отдельном браузерном этапе.

### 2.2 Хранилища, которые нельзя ломать

На текущей ветке обнаружены разные таблицы и хранилища с разными назначениями:
- `orders` — базовая очередь `core/orders`;
- `delivery_orders` и `delivery_order_assets` — рабочий UI-поток заказов/активов;
- `steam_asset_reservations` — резервации конкретных Steam asset ID;
- `steam_inventory_snapshot` и `steam_inventory_snapshot_meta` — снимки Steam-карточек;
- `game_inventory_snapshot` и `game_inventory_snapshot_meta` — отдельные снимки игровых инвентарей;
- `sent_offers.json` в локальном хранилище ASF-плагина — идемпотентность и результаты Steam trade.

Сначала нужно установить фактическое использование каждой модели и их связи. Нельзя удалять или сливать таблицы до проверки миграции и сохранности существующих заказов/резервов.

## 3. Инварианты будущей системы

1. **Подтверждённая покупка и обещанное количество.** Факт оплаты/покупки поступает из проверенного статуса площадки. Для объявления количество предметов на одну подтверждённую сделку берётся из сохранённой версии конфигурации (`delivery_quantity_per_deal`), а не из `source_amount`. Если площадка предоставляет отдельное число купленных единиц, хранить его отдельным полем и согласовать формулу обязательства; ручные корректировки допускаются только с причиной и аудитом.
2. **Единица учёта — строка заказа.** Для заказа с несколькими товарами количество считается по каждой строке отдельно; нельзя смешивать количество карточек, предметов, ключей, файлов и услуг.
3. **Единый остаток.** Для исполнения объявления остаток считается от обещанного количества по snapshot конфигурации: `remaining_to_fulfill = promised_item_quantity - reserved_item_quantity - delivered_item_quantity`. Расчёт и резерв защищаются атомарной транзакцией SQLite.
4. **Резерв до выдачи.** Нельзя выполнить обработчик без успешной резервации соответствующего количества/ресурса.
5. **Уникальные ресурсы.** Для Steam/игрового инвентаря и уникальных ключей резервируется конкретный ID/код. Один ресурс не может числиться активным резервом для двух заказов.
6. **Идемпотентность.** Повторное получение одного заказа/события/команды не создаёт второй резерв и не выдаёт товар второй раз.
7. **Неизвестный исход — блокировка.** Timeout, обрыв соединения или падение процесса после внешнего действия не трактуется как обычная ошибка. Автоматический повтор запрещён до сверки.
8. **Разделение состояний.** Подготовлено, зарезервировано, отправлено/передано, подтверждено получателем, завершено, отменено и неизвестный исход — не одно и то же состояние.
9. **Атомарное завершение.** Перенос единиц из резерва в завершённую выдачу выполняется один раз и фиксируется в аудите.
10. **Изоляция заказов.** Ошибка одного заказа не останавливает очередь; ошибки и повторы учитываются для конкретного заказа/строки/попытки.
11. **Аудит.** Резерв, освобождение, выдача, корректировка количества, ручное подтверждение и сверка имеют время, локальную ссылку на оператора/операцию и причину.
12. **Безопасность.** Ключи, токены, trade URL token, cookies и другие секреты не попадают в Git, логи, тестовые дампы или сообщения об ошибке.
13. **Deal/chat identity.** В Playerok `deal_id` идентифицирует отдельную покупку, `chat_id` — переписку; unread-счётчик/новое сообщение не создаёт заказ. Первичная baseline-сверка существующих сделок не запускает автоматическую выдачу.
14. **Общий инвентарь.** Активы всех разрешённых ботов образуют один логический пул. Конкретный `(bot_name, asset_id)` глобально резервируется только один раз, независимо от числа объявлений, которым разрешён этот предмет.
15. **Необязательный Telegram.** Telegram Bot — дополнительный канал: его недоступность не останавливает заказы; секреты защищены, входящие действия авторизуются и аудируются.

### C.2 — Доменная модель объявлений, количества и правил подтверждения

<badge>Статус: бизнес-правила по Steam Trading Cards согласованы; техническая спецификация в работе</badge>

**Цель:** согласовать точную семантику объявления, оплаченного количества наборов, Steam badge progress, общего пула карточек, резервов, многоботовых trade legs, приватности покупателя и подтверждений доставки.

####  C.2.1. Согласованные бизнес-правила Steam Trading Cards

1. **Используются только обычные Steam Trading Cards.** Foil cards / фольгированные карточки и фольгированные значки не участвуют ни в определении состава набора, ни в подсчёте запаса, ни в подборе, ни в отправке.
2. **Состав набора не задаётся вручную.** GameDelivery должен исследовать значки/наборы на Steam-профилях собственных ASF-ботов и на основании доступных данных определить для каждой игры:
   - точное количество разных обычных карточек в одном наборе;
   - идентичность каждой карточки, входящей в этот набор;
   - соответствие карточек конкретной игре/набору.
   Конкретный способ получения этих данных (доступный Steam UI/страница значка и/или поддерживаемые данные ASF) должен быть исследован и проверен на реальных профилях; не предполагать несуществующий API.
3. **Полный набор — одна карточка каждого уникального типа из установленного состава набора.** Частичные наборы в инвентаре покупателя не учитываются. Число полных наборов покупателя для игры вычисляется по количеству экземпляров каждого требуемого типа карточки: минимум по всем типам состава набора. Идентификация карточек должна опираться на проверенные устойчивые поля, а не только на отображаемое имя.
4. **Учитываются и уровень значка, и уже имеющиеся полные наборы.** Для игры целевой уровень — 5. Число наборов, которые ещё можно отправить покупателю по этой игре:
   `max(0, 5 - current_badge_level - buyer_inventory_complete_sets)`.
   Примеры: уровень 0 + 0 полных наборов → 5; уровень 3 + 0 → 2; уровень 3 + 2 → 0; уровень 0 + 5 → 0; уровень 5 → 0 независимо от инвентаря. Частичные наборы не уменьшают требуемое количество.
5. **Оплаченное количество — точное обязательство.** Если объявление обещает 10 наборов, программа должна подобрать и зарезервировать ровно 10 полных наборов. Нельзя отправить 9 или 11, нельзя намеренно исполнить часть заказа из-за нехватки запаса. Если до начала внешних действий не удалось подготовить весь объём, не отправлять ни одного trade offer, освободить только те резервы, для которых достоверно установлено отсутствие внешнего действия, и перевести заказ в ожидание решения продавца.
6. **Приоритет распределения — завершение значков до 5-го уровня.** Сначала программа ищет комбинацию игр, позволяющую довести до 5-го уровня максимально возможное число значков в рамках точного количества заказа и доступного запаса. Например, заказ на 10 наборов при наличии двух игр, которым нужно по 5 наборов, в первую очередь распределяется как 5 + 5 для двух значков уровня 5. Если после выбора максимально возможного числа завершённых значков остаётся количество наборов, остаток распределяется по другим подходящим играм, даже если он не завершит следующий значок. Подбор должен учитывать доступность полных наборов в общем пуле. Детерминированные tie-break правила для равноценных комбинаций будут уточнены в технической спецификации и тестах.
7. **Автоматический выбор игр.** Пользователь не обязан вручную выбирать игры для каждого заказа. GameDelivery самостоятельно выбирает их на основании прогресса значков покупателя, полного состава наборов и актуального общего запаса ботов.
8. **Единый логический пул всех разрешённых ботов.** Полный набор может быть собран из карточек нескольких ботов. Например, часть разных карточек находится у бота A, остальные — у бота B. Для покупателя это один полный набор. Каждый физический экземпляр при этом остаётся привязан к точному `(bot_name, asset_id)` и резервируется глобально только один раз.
9. **Несколько Steam offers в одном заказе допустимы.** Если выбранные карточки принадлежат разным ботам, родительский заказ может включать несколько независимых DeliveryLeg / Steam trade offers. Все legs вместе должны передать покупателю точный выбранный состав. Заказ нельзя считать завершённым, пока все обязательные legs не достигли согласованного подтверждённого состояния.
10. **Сообщение о невозможности полного подбора.** Если полный заказ невозможно сформировать до начала отправки, покупателю отправляется сообщение: «Подходящих карт для вашего аккаунта нет, ожидаем продавца в чате для решения проблемы». Оператору отправляется Telegram-уведомление с заказом, причиной, недостающим количеством/карточками и безопасной ссылкой на контекст сделки. Недоступность Telegram не должна приводить к потере заказа или повторной выдаче.
11. **Единый сценарий приватности.** Если профиль, значки или инвентарь недоступны из-за приватности, автоматический подбор и отправка блокируются. Покупателю отправляется одна общая инструкция открыть все необходимые настройки приватности Steam (профиль, сведения об играх/значках и инвентарь). После команды покупателя `!настроил приватность` программа повторно проверяет доступность данных и продолжает только после успешной проверки. Команда должна быть привязана к правильной сделке/покупателю и быть идемпотентной.
12. **Неизвестный результат внешней отправки.** Правило «не отправлять часть» относится к предварительному подбору и нехватке запаса до первого внешнего действия. Если несколько trade legs уже начали исполняться и внешний сбой произошёл после успешной отправки одной из них, физически откатить уже отправленный offer нельзя. В таком случае заказ фиксируется как частично исполненный/с неизвестным исходом, неуспешные и неизвестные legs не повторяются автоматически, резервы сохраняются до сверки, оператор получает уведомление. Это не является разрешением на намеренную частичную выдачу из-за недостатка карточек.

#### C.2.2. Формула подбора

Для каждой игры `g`:

- `L_g` — подтверждённый текущий уровень обычного значка покупателя (0–5);
- `S_g` — количество полных обычных наборов этой игры, уже находящихся в инвентаре покупателя;
- `R_g = max(0, 5 - L_g - S_g)` — максимально необходимое количество наборов для доведения значка до 5-го уровня;
- `A_g` — доступное количество полных наборов, которое можно собрать из общего пула наших ботов с учётом уникальных asset ID и активных резервов.

Для оплаченного заказа на `Q` наборов требуется выбрать целые неотрицательные `x_g` так, чтобы:

- `sum(x_g) = Q` — точное количество заказа;
- `0 <= x_g <= A_g` — нельзя превысить реальный доступный запас;
- приоритетная цель — максимизировать число игр, для которых `x_g = R_g` и `R_g > 0` (значок будет доведён до уровня 5);
- после достижения максимального числа завершённых значков оставшееся количество распределяется по другим подходящим играм, не превышая `R_g` и `A_g`.

Если невозможно найти распределение с `sum(x_g) = Q`, заказ не отправляется. Нельзя подменять полный заказ частичным.

Для каждого выбранного набора система должна назначить по одному конкретному asset ID каждого типа карточки из состава набора. Один набор может включать активы нескольких ботов; повторное использование одного asset ID запрещено.

#### C.2.3. Объявление и заказ

- `Listing` задаёт обещанное число наборов на одну подтверждённую покупку и разрешённый класс товара (обычные Steam Trading Cards / соответствующие наборы).
- `ConfigVersion` фиксирует неизменяемую версию настройки объявления.
- `Deal` идентифицирует отдельную покупку Playerok; `chat_id` — отдельный контекст переписки. Это разные сущности и разные идентификаторы.
- `Order` хранит snapshot конфигурации объявления, подтверждённое обязательство в наборах и общий статус исполнения.
- `OrderLine` хранит количество наборов и выбранные игры/наборы как позиции исполнения.
- `DeliveryLeg` хранит конкретный Steam offer от конкретного бота с точными asset ID и получателем.
- `DeliveryAttempt` хранит попытки, idempotency key, результат и reconciliation.
- `ResourceReservation` хранит резерв каждого физического `(bot_name, asset_id)`.

Изменение количества или настроек объявления влияет только на будущие сделки. Уже созданный заказ использует snapshot версии конфигурации, зафиксированной для этой покупки. Денежное поле Playerok (`source_amount`) не является количеством наборов.

#### C.2.4. Состояния и безопасные переходы

- Состояние сделки площадки (`PAID → SENT → CONFIRMED`) хранится отдельно от внутреннего состояния заказа и Steam offers.
- До внешней отправки заказ проходит проверку приватности, чтение badge progress и инвентаря покупателя, анализ состава наборов, полный подбор точного количества и резервирование всех требуемых активов.
- Нехватка запаса до отправки означает ноль внешних offers, сообщение покупателю и Telegram-уведомление оператору.
- Каждый offer/бот — отдельная DeliveryLeg. Успешная отправка одной leg не означает завершение всего заказа.
- Созданный Steam offer, подтверждение Steam Guard/mobile confirmation и принятие offer покупателем — разные факты.
- Timeout/падение/потеря ответа после внешнего действия — `outcome_unknown`; автоматический повтор запрещён до сверки.
- Команда `!настроил приватность` не должна повторно запускать уже выполненную отправку и не должна обходить unknown/reconciliation gate.

#### C.2.7. Утверждённый детерминированный tie-break

<badge>Статус: подтверждено пользователем 2026-11-08</badge>

Для равноценных feasible allocation действует следующий обязательный порядок:

1. Максимизировать число игр, для которых значок будет доведён до уровня 5 (`x_g = R_g`, `R_g > 0`).
2. Среди вариантов с одинаковым числом завершённых значков выбирать вариант с минимальной суммой `R_g` по выбранным для завершения играм. Рассматривать только варианты, в которых каждое завершение обеспечено запасом (`R_g <= A_g`) и весь заказ `Q` можно распределить без превышения `min(A_g, R_g)`.
3. Остаток заказа распределять по другим подходящим играм с наименьшим `R_g` (ближе к завершению), затем по возрастанию Steam AppID. Для каждой игры не превышать `min(A_g, R_g)`.
4. При полном равенстве применять лексикографический порядок Steam AppID.
5. Если точное `Q` не распределяется, не резервировать/не отправлять частичный заказ; до первого внешнего действия ни одного offer не создавать.

Это утверждённое бизнес-правило. Оно должно быть покрыто детерминированными тестами до подключения оптимизатора к рабочему delivery path.

### C.6 — Игровые предметы, инвентарь и CS2

**Цель:** расширить доставку с карточек на реальные игровые предметы, начиная с подтверждённой поддержки CS2, и предоставить безопасный единый обзор инвентаря всех выбранных ботов.

**Работы по данным и доступности:**
- Повторно использовать текущие `games/catalog.py`, `games/inventory.py`, `GameInventoryStore` и существующий UI; не создавать второй парсер без необходимости.

- Учитывать назначения одного предмета нескольким объявлениям, но глобально исключать уже зарезервированные/отправляемые активы из свободного остатка.
- Распределять точное количество одного объявления между несколькими ботами и несколькими Steam-трейдами; не требовать, чтобы все предметы находились на одном боте.
- Хранить `tradable` и `marketable` отдельно от причины ограничения. Различать `none`, `market_purchase_cooldown`, `trade_protection`, `permanently_non_tradable` и `unknown`; один `tradable=false` сам по себе не доказывает постоянную блокировку или её причину. `unknown` никогда не трактуется как доступное.
- Не смешивать Trade Protection и Market Purchase Cooldown. Trade Protection для CS2 после получения предмета через обмен действует 7 дней от подтверждения обмена; предмет помечается в Inventory/trading interface, его нельзя передавать, изменять или перемещать в Storage Unit, а защищённый обмен можно отменить. Для предметов, купленных в игре или на Community Market, Steam указывает индивидуальную дату доступности в инвентаре; не задавать фиксированные 7 дней и не отсчитывать срок от первого обнаружения.
- Сохранять `tradable_after` только как точный timestamp с timezone из подтверждённого источника. По аудиту ASF Generic 6.3.11.7 в `CEconItem_Description` нет типизированного поля `tradable_after`; числовые `market_tradable_restriction` и `market_marketable_restriction` не являются абсолютной датой. Не превращать их или локализованный текст в срок до подтверждения семантики и формата.
- По достижении нуля таймера запрашивать актуальный инвентарь через ASF. Само истечение локального таймера не переводит предмет в tradable: доступность меняется только после нового снимка, подтверждающего `tradable=true`.
- Установить единое правило резерва: резервировать можно только экземпляр с подтверждённым `tradable=true`, свежим снимком и отсутствием другого активного резерва. `false`, trade-locked и `unknown` не резервируются вообще и не попадают в автоматически сформированный состав заказа.
- Перед резервированием и непосредственно перед отправкой перепроверять состояние доступности; при смене статуса освобождать/не создавать резерв и исключать такой asset из отправки. UI-фильтр не является единственной защитой — правило обязательно проверяется доменным сервисом/БД и delivery preflight.
- После подтверждения источника расширить модель экземпляра данными `restriction_type`, `restriction_source`, `restriction_status`, nullable `tradable_after` и временем последнего inventory refresh; сохранить `amount` из ASF. Любое расширение SQLite/migrations — отдельный будущий этап. Старые записи и любые поля без достоверного значения остаются `unknown` до нового ASF snapshot.
- Проверить установленную версию ASF, её `/swagger`, актуальные контракты и допустимый способ отправки именно AppID 730/context 2.
- Проверить ограничения ASF/Steam для каждого типа предметов, возможность выбора/передачи точного asset ID и получения результата.
- Создать отдельный `games/cs2` handler только после подтверждения реального способа доставки.
- Сохранять метаданные CS2 (quality, rarity, exterior, StatTrak и прочие доступные tags) в отображении; характеристики не должны влиять на идентичность asset ID.
- Для Dota 2/TF2/Rust и будущих игр подключать новые обработчики только по отдельным проверенным правилам.

**Критерии приёмки по доставке:**
- Предпросмотр показывает точную игру, бота, получателя и список предметов.
- Проверяется свежий ASF inventory и подтверждённый tradable-флаг каждого asset.
- Ни один locked, non-tradable или unknown asset не может попасть в резерв или отправку, в том числе при вызове сервиса напрямую в обход UI.
- После предполагаемого окончания конкретного ограничения предмет становится кандидатом на резерв только после свежего ASF snapshot с `tradable=true`; истечение локального таймера не меняет состояние.
- Передача CS2 не использует card-only проверку 753/6 и не отправляет карточки вместо игровых предметов.
- Тестовая отправка подтверждена на отдельном аккаунте, либо capability явно остаётся disabled/unsupported.
- Никакая поддержка не объявляется готовой по одному лишь наличию инвентаря/парсера.

### C.11 — Полная регрессия и приёмка этапа C

**Цель:** доказать совместимость всех обработчиков и безопасную работу очереди.

## 5. Решения, которые должны быть зафиксированы до реализации соответствующих блоков

1. **Связь Playerok deal/listing/chat.** Скриншоты показывают UUID в пути `/deal/<UUID>` и отдельный UUID в `/chats/<UUID>`. В браузерном этапе нужно проверить, что deal UUID стабилен и однозначно принадлежит сделке, а listing ID можно надёжно получить из карточки/страницы сделки. При невозможности получить точный ID автодоставка блокируется.
2. **Первичная синхронизация Playerok.** Предлагаемый безопасный default: все найденные при первичном baseline deal ID записываются как уже известные без автоматической выдачи; импорт старых неоплаченных/неисполненных сделок выполняется отдельным явным действием. Требуется проверить полноту обхода чатов/пагинации и определить ручной сценарий восстановления незавершённого baseline.
3. **Количество на одну покупку.** Пользователь задаёт `delivery_quantity_per_deal` в версии конфигурации объявления. Если площадка в будущем отдаёт собственное число покупаемых единиц, определить как оно умножает/согласуется с настройкой на одну покупку; до подтверждения не выводить это из суммы сделки.
4. **Момент учёта Steam delivery.** Разделять созданный offer, подтверждение ASF/mobile и принятие получателем. Точное условие перехода в delivered и момент освобождения резерва определить с учётом нескольких delivery legs.
5. **Частичная отправка на несколько ботов.** Рекомендуемое безопасное правило: до первой внешней отправки зарезервировать полный требуемый состав со всех выбранных ботов. Если полный состав собрать нельзя — не начинать отправку автоматически. Если одна из уже начатых legs завершилась неизвестно или другая не удалась после успешной отправки первой, сохранять частичный/unknown статус и сверять только незавершённые legs; успешные не повторять.
6. **Telegram proxy/действия.** Выбрать и проверить поддерживаемые схемы proxy на реальном сетевом клиенте; подтвердить, какие команды/ответы можно безопасно выполнять через Bot API и проверенный Playerok browser/adapter path. Токен хранить только в системном хранилище.
7. **Файлы и прочие площадки.** Автоматическая передача возможна только после проверки реальной возможности конкретной площадки. Само наличие файла не считается доставкой.
8. **Причина блокировки и countdown.** Раздельно проверять Trade Protection и Market Purchase Cooldown. Не выводить тип ограничения из одного `tradable=false`; без доказанного `tradable_after` таймера нет. По достижении любого срока требуется новый inventory refresh и подтверждение `tradable=true`.
9. **Счётчики инвентаря.** В списочном режиме считать физические экземпляры и разделять total/tradable/non-tradable/unknown. Не включать unknown в подтверждённо tradable и не объединять разные варианты предмета по одному лишь названию.

Эти решения должны быть закрыты в соответствующем блоке до изменения схемы/кода.

#### C.6.2 — CS2 Inventory View Model design checkpoint (2026-11-08; no implementation)

Flow: ASF IPC → `games/inventory.py::parse_game_inventory` joins Assets/Descriptions by classid+instanceid → `InventoryItem` → `GameInventoryStore` per-bot snapshot → selected owners in `GameInventoryPanel` → `GameItemCard`. CS2 catalog is 730/2. Current parser/model/store lose appid, contextid, amount, typed restriction metadata and per-item refresh timestamp; DB is out of scope. Steam cards already have `InventoryView/InventoryRow`, `assets_by_bot`, and dedup in `games/steam_cards/inventory_views.py`, but `CardCopy` has different semantics and only one tradable flag; do not reuse as CS2 domain type.

Proposed immutable `CS2InventoryInstance`: physical key `(game_id, bot_name, asset_id)`; appid/context_id optional ints; asset/class/instance IDs strings; `amount: int | None`; name/type/market hash; independent `tradable` and `marketable: bool | None`; preliminary restriction type `none|market_purchase_cooldown|trade_protection|permanently_non_tradable|unknown`, source nullable, status `available|restricted|unknown` (names and transitions need review); trusted `tradable_after` and `last_inventory_refresh` nullable; preserve existing visual metadata. Do not infer missing source data; decide whether a separate in-memory adapter is needed before implementation.

Group by stable item identity `(appid,class_id,instance_id,market_hash_name-or-name)` and include restriction status/type and both flags so restricted/unknown variants never merge. Dedup only full physical key; reject conflicts. Preserve every owner and asset ID. Sum only valid supplied amounts; unknown amount is separate, not assumed 1. Compute unique bot count, available (fresh + tradable true + clear status), unavailable and unknown totals independently. Card/table render from the same projection.

State rules: cause requires a proven source; tradable=false alone → unknown; expired countdown does not unlock; only a new ASF snapshot can change eligibility; marketable is independent; unknown is never reservable. Mock cases: multi-bot grouping, same asset ID cross-bot, duplicate/conflict, stable order, variant and restriction separation, independent flags, absent cause/time/amount, stack sums, fresh/expired snapshot, bot count and all quantity totals, card/table parity, selected-bot filtering, no 730/16 merge, and no DB/store/UI/ASF/preflight/trade calls.

Separate small implementation plan, pending contract review: add only immutable CS2 projection + pure builder and mock tests. If `InventoryItem` cannot supply fields, stop for a separate in-memory source-adapter design. No DB/schema/UI/production/trade/plugin/market changes.

#### C.6.3.6 — OpenSkin Pricing API v1 и оценка стоимости инвентаря CS2 (исследование/план, ожидает согласования)

9 ноября 2026 проверена официальная документация и OpenAPI OpenSkin. v1 Pricing API остаётся бесплатным, без API key, коммерческое использование заявлено разрешённым; отдельно существует Platform API v2 с key/тарифами, его не использовать. Единственный целевой host: `https://api.openskin.dev`, endpoint batch: `POST /v1/prices/batch`.

Batch принимает не более 500 строк `market_hash_name` либо объектов `{item, pattern}`; ответ `results` упорядочен как запрос и сохраняет несколько pattern-вариантов одного имени, тогда как `data` map перезаписывает дубли имени. Матчить только упорядоченный массив и сверять echoed item/pattern. Для оценки использовать исключительно `steam.ask`; OpenAPI задаёт `number | null`, USD и item-level `steam.updated_at`. JSON-числа разбирать через Decimal, кэшировать точную десятичную строку. Не использовать median, bid, другие marketplaces или неявную конвертацию валют. Источник обновляет Steam order book примерно каждые 6 часов, median/volume — ежедневно. 10-минутная проверка должна оставаться локальной, не отправляя лишний batch до допустимого обновления; `source_updated_at` и локальный `fetched_at` независимы.

ASF CS2 source — один существующий GET 730/2; catalog подтверждает AppID 730. Snapshot хранит по записи на физический asset. Текущие модели содержат market hash, владельца/asset ID, quality/exterior/rarity/tags и tradable flags; typed pattern/paint seed/float отсутствуют. Поэтому Steam ценовая identity предлагается как `(appid=730, exact market_hash_name, exact pattern-or-null)`. Для pattern-sensitive варианта без точного источника pattern не назначать общий ask, а показать цену unknown/unsupported. Запросы не содержат BotName, asset ID или данные аккаунта.

SQLite proposal: одна новая таблица `cs2_price_cache` в существующей базе GameInventoryPanel, с composite key `(appid, source, market_hash_name, pattern)` и точными полями цены, валюты, source/fetched timestamps, last success/attempt, state и HTTP error code. Кэш оставить отдельно от snapshot; физический ключ инвентаря и legacy schema не менять. Текущие game inventory store tables уже создаются идемпотентно `CREATE TABLE IF NOT EXISTS`; общего versioned-migration каталога для них нет. На временной ошибке last good quote сохраняется и отображается как stale, отсутствие/null/invalid ask не становится нулём.

Расчёты — через Decimal и количество физических asset rows, а не ASF amount. Включать непередаваемые и unknown assets. Общий режим показывает unit price и стоимость физических экземпляров группы; по-asset режим показывает отдельную цену asset; сводка показывает стоимость каждого выбранного бота и выбранный итог, свежую/устаревшую оценку и счётчик неизвестных цен. Обнаружено несоответствие: текущий `separate` режим фактически разделяет по ботам, но ещё объединяет одинаковые assets внутри бота. Для выполнения требования per-asset нужен CS2-only рендер одной строки/карточки на physical asset; остальные игры не менять. OpenSkin запросы запускать асинхронно, batch ≤500, по одному in-flight, учитывать ошибки/Retry-After; timer каждые 10 минут оценивает локальную свежесть относительно документированной Steam cadence.

#### C.6.3.6.2 — диагностика OpenSkin proxy (2026-11-09)

Код подтвердил причину неоднозначного сообщения «сервис недоступен»: прежняя connection check была фактически ценовым POST, поэтому смешивала proxy transport с доступностью API; когда Qt завершал запрос без HTTP status, отображение теряло `QNetworkReply.error()`/`errorString()`. Открытие `openskin.dev` в браузере не подтверждает доступность `api.openskin.dev/v1/prices/batch`. Это доказывает дефект диагностики, но без старого response/log или нового локального результата не устанавливает конкретный источник сетевого отказа пользователя.

Проверки разделены. Кнопка proxy check выполняет `GET https://api.openskin.dev/` с `Range: bytes=0-0` через тот же локальный Qt proxy transport; ответ, кроме HTTP 407, означает, что HTTPS/TLS endpoint вернул HTTP status, но не подтверждает работу pricing API. Qt transport errors дают безопасную категорию и detail; HTTP 403/407/429/5xx различимы. Проверка SSL-сертификатов не ослаблялась.

Proxy назначается только на `QNetworkAccessManager` OpenSkin до запроса; его глобальная конфигурация не меняется. Поддержаны HTTP CONNECT и SOCKS5 с auth callback и удалённым DNS capability. Это соответствует [Qt QNetworkAccessManager](https://doc.qt.io/qtforpython-6/PySide6/QtNetwork/QNetworkAccessManager.html) и [Qt QNetworkProxy](https://doc.qt.io/qtforpython-6/PySide6/QtNetwork/QNetworkProxy.html). #### C.6.3.6.3 — предотвращение ожидания уже завершённого QNetworkReply (2026-11-09)

`_qt_proxy_request()` подключал `finished` к event loop после выдачи запроса, но без проверки текущего состояния всегда запускал ожидание. По контракту Qt reply может быть уже завершён до получения сигнала `finished`, а `isFinished()` предназначен для проверки этого случая ([QNetworkReply](https://doc.qt.io/qtforpython-6/PySide6/QtNetwork/QNetworkReply.html)). Если сигнал был пропущен, таймер мог сработать после завершения и породить ложную диагностику timeout до `requestSent`.

Теперь event loop и timeout запускаются только если `reply.isFinished()` равен false; таймер останавливается в `finally`. Regression test имитирует уже завершённый reply и гарантирует отсутствие ожидания/таймера. `tests.test_openskin_proxy` — 19 passed, exit 0; compileall двух затронутых Python-файлов — exit 0; `git diff --check` — exit 0 с одними line-ending warnings. Live proxy check не выполнялся, поэтому локальный результат пользователя нужен для подтверждения устранения данного timeout. HEAD неизменён, commit/push не выполнялись.
