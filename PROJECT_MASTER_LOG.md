## 3. Глобальные архитектурные решения

### 3.1 Модульный монолит

Выбрано пользователем: один настольный продукт, локальная БД и отдельные модули с явными контрактами. Не переходить к микросервисам без отдельного решения пользователя.

Правила границ:
- UI не содержит бизнес-правил.
- Marketplace adapters не изменяют ядро заказа напрямую.
- Игровые модули описывают игровые типы/активы.
- Delivery handlers отвечают за конкретные методы доставки.
- Сервисы ядра управляют оплатой/правом на выдачу/резервами/журналом.
- Новые площадки, игры и методы доставки подключаются через версионированные контракты и тесты совместимости.
- Добавлять только необходимые модули по мере наступления соответствующего этапа; не создавать массовый пустой каркас заранее.

### 3.2 Игровые и цифровые товары

Тип товара и механизм доставки — разные понятия.

Запланированные категории:
- Steam Trading Cards — существующий модуль сохранить и расширять.
- Предметы CS2 и других игр — самостоятельные игровые модули; не путать с коллекционными карточками Steam.
- Цифровые ключи/коды/лицензии.
- Файлы.
- Услуги.
- Будущие категории — через подключаемые реализации.

Способ доставки подбирается независимо от категории товара. Для Steam-инвентаря/торговли сохраняется правило: использовать ASF, не прямой Steam Web API.

### 3.3 Учёт оплаченного количества и защита от oversell

Запланированный общий принцип для ресурсов выдачи:

`remaining_to_fulfill = promised_item_quantity - reserved_item_quantity - delivered_item_quantity`

Для Playerok подтверждённая покупка определяет факт возникновения обязательства, а количество игровых предметов на одну покупку задаётся в настройке конкретного объявления (`delivery_quantity_per_deal`). Денежная сумма сделки не является количеством. Если площадка отдельно предоставляет число купленных единиц, его нужно хранить отдельно и согласовать с количеством выдачи по объявлению.

- Для каждого заказа сохраняется неизменяемый снимок версии конфигурации объявления, включая количество, предметы и разрешённых ботов.
- Проверять остаток атомарно в БД при резервировании полного состава и перед каждой фактической отправкой.
- Один физический asset ID учитывается в общем пуле всех ботов и может быть зарезервирован только один раз, даже если назначен нескольким объявлениям.
- Хранить журнал резервов, фактических выдач, отмен, корректировок и отдельных delivery legs.
- Повторные команды должны быть идемпотентными на уровне заказа и каждой отдельной отправки.
- Неизвестный исход отправки не считать неудачей и не запускать автоматический повтор; требуется сверка.
- Ошибка одной отправки не должна останавливать обработку остальных заказов; родительский заказ не считается завершённым, пока все обязательные legs не подтверждены.

### 3.4 Автоматизация сообщений покупателям

Выбрано пользователем: автоматизация с настройками и возможностью ручного подтверждения.

Запланированные требования:
- глобальные шаблоны по умолчанию;
- индивидуальные шаблоны для конкретного объявления/товара;
- сценарии по событиям заказа;
- переменные шаблонов (например, имя покупателя, ID заказа, товар, количество);
- предпросмотр итогового текста;
- задержки, лимиты и идемпотентность;
- история сообщений и статусы;
- режим автоматической отправки и режим ручного подтверждения;
- отключение сценария на уровне объявления/площадки;
- безопасное поведение при ошибке площадки.

### 3.5 Встроенный браузер и сценарии площадок

Пользователь уточнил: вход в каждую площадку и управление ею должны происходить через встроенный браузер с настройками сценариев и функций; у Playerok нет собственного API-ключа, поэтому выбран браузерный способ автоматизации.

Целевое направление:
- встроенный browser subsystem, интегрированный в PySide6;
- отдельные профили/сессии по площадкам и аккаунтам;
- площадки подключаются через изолированные адаптеры;
- пользователь видит браузер и может вручную завершить вход/дополнительную проверку;
- общий движок сценариев выполняет действия по явным шагам;
- визуальный конструктор сценариев — обязательная пользовательская функция;
- расширенный режим пользовательских скриптов — предусмотреть, с версионированием, экспортом/импортом, проверкой, откатом и ограничением разрешений;
- скриптам не давать произвольный доступ к секретам, внутренней БД и любым операциям приложения;
- поддержать ожидания элементов, ограниченные повторные попытки, таймауты, скриншоты, логи и остановку при CAPTCHA/неожиданной проверке;
- опасные действия (публикация, удаление, изменение объявления, важное сообщение) требуют явного контроля и настраиваемого подтверждения.

Qt WebEngine предложен как основной кандидат для встроенного отображаемого браузера в PySide6. Конкретный стек/механизм автоматизации и изоляции сценариев **ещё не утверждён окончательно** и должен быть исследован в рамках соответствующего этапа до кода. Не считать Playwright/CDP/Qt WebEngine архитектуру реализованной.

### 3.6 Playerok и прочие площадки

Пользователь выбрал постепенное расширение:
1. вход и профиль;
2. объявления: просмотр/создание/редактирование — в пределах проверенных возможностей интерфейса и правил площадки;
3. сообщения и шаблоны;
4. автоматизация общения;
5. прочие операции аккаунта и заказов;
6. подключение других площадок.

Существующий read-only адаптер Playerok не удалять до тех пор, пока браузерный поток не обеспечивает проверенную замену. Сначала изучить существующие приватные веб-эндпоинты и интерфейс сайта; не придумывать несуществующие API/операции. Возможности каждой площадки объявлять только после проверки.


### 3.7 Идентификация сделок и чатов Playerok — защита от ложных новых заказов

Пользователь показал две страницы Playerok:
- страница отдельной сделки имеет URL вида `/deal/<UUID>` — кандидат на уникальный внешний `deal_id`;
- страница переписки имеет URL вида `/chats/<UUID>` — отдельный `chat_id`, который связывает коммуникацию с покупателем.

Это визуально подтверждённые примеры формата URL по скриншотам, но стабильность и доступность этих ID должны быть дополнительно проверены на живом интерфейсе перед реализацией.

**Основные правила:**
- Один чат может содержать несколько старых и новых покупок. Каждая сделка — самостоятельный заказ с собственным `deal_id`; `chat_id` — только контекст переписки и маршрут ответа.
- В локальном реестре хранить наблюдения по ключу `(marketplace_account_id, deal_id)`, с уникальным ограничением и ссылкой на `chat_id`, listing ID, статус и время обнаружения.
- При первом подключении аккаунта сделать baseline-сверку уже существующих сделок: записать их ID как исторически известные и не запускать автоматическую выдачу по ним. Автоматическую обработку новых сделок включать только после завершения полной сверки.
- Если baseline неполон (ошибка загрузки, недоступные страницы/пагинация, не удалось открыть часть чатов), выставлять состояние синхронизации «не завершена» и блокировать автоматическую обработку новых заказов до явной сверки.
- После baseline новый заказ-кандидат создаётся только при появлении ранее неизвестного `deal_id` и подтверждённом статусе оплаты. Изменение статуса уже известной сделки обновляет её состояние, но не создаёт второй заказ.
- Счётчик непрочитанных чатов/сообщений служит только сигналом проверить переписки. Он не является доказательством новой покупки.
- Новое сообщение в существующем чате — отдельное событие сообщения/уведомления, но не событие нового заказа.
- Повторный scan, обновление страницы, смена сортировки, повторное появление сделки и повторная доставка события не должны создавать дубль.
- Если точный `deal_id` или связь сделки с объявлением не извлечены, запись направляется на ручную проверку; нельзя подменять ID сделки ID чата, именем покупателя или последней открытой карточкой.
- Старые незавершённые сделки при необходимости импортировать отдельным явным действием оператора после проверки, а не автоматически при первом подключении.

### 3.8 Объявления и общий пул предметов всех ботов

Встроенный браузер должен позволять открыть/настроить каждое объявление и связать его с локальной конфигурацией выдачи.

**Конфигурация отдельного объявления:**
- внешний listing ID и URL/название для отображения;
- количество предметов, выдаваемых за одну подтверждённую покупку (`delivery_quantity_per_deal`);
- один или несколько селекторов конкретных типов предметов;
- разрешённые боты-источники и приоритет/правило распределения;
- состояние конфигурации и версия.

Один и тот же селектор предмета можно привязать к нескольким объявлениям, а одно объявление может разрешать несколько предметов/вариантов. Физические активы при этом не дублируются в остатках: общий пул и резервации должны работать поверх инвентарей всех ботов.

**Принципы общего инвентаря:**
- Синхронизировать снимки всех ботов и сохранять владельца каждого актива (`bot_name + asset_id`).
- Показывать общий доступный остаток по селектору/объявлению с учётом свежести снимков, tradable-проверок, активных резервов и незавершённых отправок.
- Один и тот же предмет, разрешённый для двух объявлений, доступен только в одном глобальном количестве. Продажа по одному объявлению сразу уменьшает общий остаток для остальных.
- При заказе разрешается собрать указанное количество с нескольких ботов; не требуется, чтобы все одинаковые предметы лежали на одном аккаунте.
- Один заказ может породить несколько отдельных Steam-трейдов/отправок — например, по одной или несколько от разных ботов. Каждая отправка содержит конкретного бота и точный список asset ID.
- Перед первой отправкой по умолчанию требуется зарезервировать полный требуемый состав. Если полного количества нет, автоматическую отправку не начинать. Если после старта часть отправок уже прошла, родительский заказ получает частичный/неизвестный статус; уже успешную отправку повторять нельзя, незавершённые legs сверяются отдельно.
- Изменения конфигурации объявления влияют только на будущие покупки; старый заказ исполняется по сохранённому snapshot.

### 3.9 Telegram Bot — уведомления и двусторонние действия

Telegram Bot — настраиваемая дополнительная панель уведомлений и управления, а не обязательная зависимость основного delivery pipeline.

**Настройки и события:**
- Bot token, ID целевого чата и allowlist Telegram user/chat IDs.
- Прокси для Telegram Bot API и получения обновлений; типы прокси объявляются поддержанными только после проверки выбранного HTTP-клиента и тестов.
- Отдельные кнопки «Проверить подключение» и «Отправить тестовое сообщение» с раздельными понятными результатами.
- Настраиваемые уведомления о новых оплаченных сделках, новых сообщениях покупателей, нехватке предметов, резервации и распределении по ботам, ходе отправок, создании offer/ожидании подтверждения, завершении, ошибках, неизвестном результате, необходимости ручной сверки и потере/восстановлении браузерной сессии.
- Настройки включения каждого события, шаблонов, подробности и ограничений по объявлениям.

**Ответы и безопасность:**
- Оператор может ответить прямо на Telegram-уведомление о конкретной сделке. Reply-to message/callback должен однозначно восстанавливать order ID → deal ID → chat ID; отправка ответа в Playerok выполняется через проверенный adapter/browser path.
- Команды и ответы принимаются только от allowlist-пользователей; все действия журналируются и подчиняются тем же настройкам ручного подтверждения, шаблонам, задержкам и лимитам, что и приложение.
- Bot token и proxy credentials хранить в системном секретном хранилище, не записывать в логи и не показывать в UI.
- Повторные Telegram updates и callbacks должны быть идемпотентными.
- Недоступность Telegram не должна останавливать обработку заказов: уведомления ставятся в outbox и безопасно отправляются после восстановления связи.

### 3.10 Доступность обмена и два формата инвентаря

Приоритет: не допускать резервирования предметов, которые сейчас нельзя передать, и позволить быстро оценивать распределённый по аккаунтам запас.

**Текущая исходная точка, проверенная по коду:**
- `app/game_inventory_panel.py` уже содержит `transfer_filter` со значениями «Любая передаваемость», «Передаваемые», «Непередаваемые», «Не проверена». Этот фильтр нужно расширить/переиспользовать, а не создавать второй независимый.
- `GameInventoryPanel` уже выводит предметы в существующем карточном виде с иконками. Его текущий список — только карточная сетка; компактный агрегированный список по типам предметов ещё требуется.
- `app/inventory_panel.py` также имеет режим карточек и подробную таблицу отдельных экземпляров, но эта таблица не заменяет целевой агрегированный список, который группирует одинаковые предметы и показывает сводные количества.
- `games/inventory.py::InventoryItem` содержит `is_tradable: bool | None`, но проверенный parser/snapshot пока не хранит timestamp разблокировки trade lock.

**Правила доступности и резервации:**
- Состояния предмета: `tradable` (ASF подтвердил `true`), `not_tradable/locked` (подтверждён `false` или trade ban) и `unknown` (нет достоверных данных/снимок устарел).
- Резерв и доставка разрешены только для предметов с подтверждённым `tradable=true`, актуальным inventory snapshot и отсутствием другого резерва.
- Предмет с trade ban/`tradable=false` не резервируется до фактической разблокировки. `unknown` также не резервируется — неизвестность не трактуется как разрешение.
- Если ASF/Steam предоставляет достоверное структурированное время разблокировки, сохранять его как timestamp с timezone и показывать обратный отсчёт. Не вычислять время по локальным часам, приближённым правилам или ненадёжным локализованным текстам.
- По достижении нуля таймера обновить инвентарь через ASF. Не делать предмет доступным только по истечению локального таймера: требуется новый ответ ASF с `tradable=true`. Если точной даты нет, показывать, что время разблокировки неизвестно.
- Проверки повторяются в сервисе резервации и непосредственно перед отправкой; UI-фильтр/приглушение сами по себе не являются защитой.

**Два формата отображения:**
- Сохранить существующий карточный формат и добавить переключение на компактный списочный формат. Ничего не удалять из работающего карточного вида; предпочтение пользователя сохранять между запусками, если это не ломает текущие настройки.
- В списочном формате объединять одинаковые предметы по устойчивой идентичности (`game/app-context + class/instance + значимые характеристики варианта`), а не только по названию.
- Строка: компактная иконка, название и подтип/качество; по возможности число аккаунтов-владельцев; справа счётчики «Всего» белым, «Обмен» зелёным, «Не обмен» красным.
- Предметы с блокировкой отображать в общем списке, но визуально приглушать/делать более прозрачными и снабжать индикатором замка или таймера. Это не удаляет их из учёта и не разрешает резерв.
- Непроверенные экземпляры считать отдельно нейтральным цветом/индикатором, не прибавлять к подтверждённо передаваемым и не смешивать с подтверждённо заблокированными.
- Фильтр доступности должен одинаково работать в карточном и списочном форматах: все, только передаваемые, непередаваемые/заблокированные, не проверенные.
- Агрегированные количества считаются по выбранным аккаунтам и должны сохранять возможность раскрыть владельцев и отдельные asset ID.

### 3.11 Жизненный цикл Steam trade offer и статусы доставки

**Подтверждённая исходная точка:** 2026-11-07 пользователь сообщил, что GameDelivery успешно отправил Steam trade offer. Текущий видимый статус `Sent - ожидание покупателя` уже существует. Следующая задача — не просто фиксировать отправку, а отслеживать дальнейшее состояние каждого Steam offer и связывать его с delivery leg и родительским заказом.

**Обязательные статусы и переходы:**
- `Sent - ожидание покупателя` — offer создан и отправлен; программа ожидает решение покупателя. Нельзя считать этот статус завершённой доставкой.
- `Принят покупателем` — Steam подтвердил принятие конкретного offer покупателем. Факт должен поступить из авторитетного состояния Steam/ASF, а не из локального предположения или факта мобильного подтверждения отправителя.
- `Отклонен покупателем` — Steam подтвердил, что покупатель отклонил offer. По этому событию обязательно отправить уведомление в Telegram Bot.
- Для одного заказа с несколькими delivery legs сохранять статус каждой отправки отдельно. Родительский заказ становится полностью принятым/доставленным только после подтверждения всех обязательных legs. Частичное принятие/отклонение должно быть видно отдельно и не должно скрывать уже успешные отправки.

**Будущая автоматизация площадки:**
- Событие `Принят покупателем` в будущем должно запускать сценарий площадки, который открывает соответствующую сделку и нажимает «Выполнен заказ».
- Триггер разрешён только после авторитетного подтверждения принятия всех обязательных Steam offers по заказу. До реализации сценария нажатия кнопки это только зафиксированное требование, а не существующая функция.
- Запуск сценария площадки — одноразовый и идемпотентный: повторное получение Steam-статуса, перезапуск программы или повторная обработка outbox не должны повторно закрывать сделку. Записывать результат и время попытки.

**Ошибки и пользовательские статусы:**
1. **Инвентарь покупателя скрыт.** Показать покупателю объяснение и инструкцию, как открыть инвентарь и настроить приватность. Завершить сообщение точной фразой: «После того как откроете инвентарь, отправьте команду `!настроил приватность`.» Для заказа выставить отдельное состояние ожидания настройки приватности (отображаемая подпись: `Инвентарь скрыт — ожидание настройки приватности`). Команда может инициировать повторную попытку только после всех проверок из раздела 3.12.
2. **Покупатель не может обмениваться.** Выставить отдельное состояние (рабочая подпись: `Ограничения на обмены — требуется ручное решение`), отправить покупателю сообщение и обязательно уведомить Telegram Bot. На текущем этапе никакой автоматической попытки обхода/повтора не делать: требуется ручное устранение причины покупателем или оператором и последующая явная повторная проверка. Архитектура должна позволять позднее подключить отдельный автоматический resolver, но он выключен и не реализуется без отдельного решения.

Шаблон сообщения для второго случая, подлежащий редактированию в настройках:
> На вашем аккаунте ограничения на обмены. Возможно, мобильный аутентификатор подключён менее 15 дней или не подключён вообще. Также если вы меняли игровой никнейм, на аккаунте может действовать временное ограничение на обмены (обычно 2–4 часа). Проверьте ограничения Steam и после их снятия обратитесь к нам для повторной проверки.

Примечание: срок «2–4 часа» и связь именно со сменой игрового никнейма сохранить как пользовательский текст/гипотезу до технической проверки по официальным правилам Steam; не зашивать это как универсальную причину или гарантированный срок. Сообщения и сроки должны быть настраиваемыми.

**Расширяемость статусов:**
- Предусмотреть реестр статусов и переходов, а не жёстко зашитый список из четырёх значений. Для нового состояния задаются стабильный внутренний ключ, отображаемое название, категория (ожидание/успех/ошибка/ручная проверка), допустимые переходы, автоматические действия, Telegram-события и шаблоны сообщений.
- Сохранять неизвестные/новые состояния без потери исходного значения и безопасно переводить их в ручную сверку. Неизвестный статус никогда не трактовать как «принят».
- Хранить историю переходов: источник события, время, старый и новый статус, идентификатор Steam offer, order ID и delivery leg ID, диагностическую причину без секретов.

### 3.12 Команды покупателя и защита от повторной отправки

**Система команд:** команды покупателя должны быть отдельным расширяемым реестром: имя/алиасы, назначение, допустимые состояния заказа, проверка личности, требуемые разрешения, идемпотентность, лимиты, обработчик и шаблон ответа. Команда не должна исполняться только по совпадению текста: сначала установить, от какого подтверждённого покупателя и по какой конкретной сделке получено сообщение.

**Первая обязательная команда:**
- `!настроил приватность` — покупатель сообщает, что открыл инвентарь. Команда привязывается к конкретной сделке и разрешена только пока заказ находится в состоянии ожидания настройки приватности. После обработки статус не должен оставаться доступным для повторного запуска команды без новой отдельной попытки, созданной системой.

**Дополнительные полезные команды (предложение для будущего согласования):**
- `!статус` — вернуть покупателю актуальный статус его заказа и кратко объяснить следующий шаг; никаких действий по повторной отправке не выполняет.
- `!помощь` — показать список доступных команд и общую инструкцию.
- `!поддержка` — создать запрос оператору и отправить уведомление в Telegram; не менять статус доставки.
- `!неполучил` — сообщить о проблеме с получением, прикрепить обращение к конкретному заказу и уведомить Telegram; не запускать повторную выдачу автоматически.
- `!инвентарь` — выдать инструкцию по настройке видимости инвентаря; само по себе не запускает повторную отправку.

Список команд должен быть настраиваемым и расширяемым. Не добавлять универсальные команды вроде `!повторить`, которые без проверки могут вызвать дублирующую отправку. Для нераспознанной команды — безопасная подсказка, без изменения состояния заказа.

**Обязательная защита от повторной отправки после `!настроил приватность`:**
1. Проверить, что сообщение пришло от того же Steam/marketplace buyer identity, который привязан к конкретному заказу, и относится к правильной сделке/чату.
2. Проверить, что заказ всё ещё ожидает настройки приватности, не принят, не закрыт, не отменён и не находится в состоянии `unknown`/ручной сверки.
3. Проверить журнал попыток и все известные Steam offer ID этого заказа. Если offer уже создан, отправлен, принят, отклонён или имеет неизвестный исход, не создавать новый автоматически; сначала сверить реальное состояние в Steam/ASF.
4. Использовать уникальный idempotency key для попытки повторной отправки (как минимум order ID + delivery leg ID + номер разрешённого retry generation) и БД-ограничение от параллельных/повторных запусков. Повторные копии одного сообщения должны обрабатываться один раз.
5. Перед новой попыткой заново получить inventory snapshot через ASF и проверить конкретные зарезервированные asset ID: они существуют у нужного бота, принадлежат нужному инвентарю, всё ещё передаваемы и не включены в другой offer.
6. Сначала надёжно записать начало попытки и её ключ, затем выполнить отправку. При timeout/обрыве/неизвестном результате не считать отправку неудачной и не повторять её автоматически — сначала reconciliation по Steam offer ID/истории ASF.
7. После создания offer атомарно сохранить его Steam offer ID, связь с order/delivery leg и состояние `Sent - ожидание покупателя`. Та же команда после этого не может породить второе предложение.
8. Если покупатель уже принял предложение, поздняя команда `!настроил приватность` должна быть проигнорирована как устаревшая; никаких дополнительных предметов отправлять нельзя.

**Резервация — важная, но не единственная защита:** уже имеющееся резервирование asset ID помогает не продать/не назначить тот же физический предмет другому заказу. Однако само по себе оно НЕ предотвращает повторное создание двух offers для одного заказа и не доказывает, что прежний offer не был отправлен. Нужны также уникальные попытки/idempotency key, запись Steam offer ID, блокировка параллельного выполнения, сверка исхода `unknown` и повторная проверка статуса заказа/резерва перед каждым side effect. При принятом offer резерв переводится в учёт фактически доставленного количества; при отклонённом/неизвестном offer сначала обновить инвентарь и выполнить сверку, не отправлять автоматически второй раз.

### 3.13 Обобщение инвентаря и доставки на предметы любых игр

Сейчас вкладка/поток заказов позволяет выбирать предметы и отправлять их только из Steam Trading Cards, хотя отдельная общая игровая инвентарная основа уже существует. Требуется подключить её к заказам и доставке:
- В заказе должна быть возможность выбрать активы из инвентарей разных игр, а не только карточки Steam.
- Сохранить текущий модуль Steam Trading Cards как один из типов активов; не удалять и не ломать его рабочую логику.
- Универсальный inventory/delivery contract должен передавать игру, AppID/context ID, идентификатор типа/варианта, asset ID, бота-владельца, количество/характеристики, tradable state и нужные данные для точной отправки.
- Для Steam-предметов использовать ASF и проверенные методы ASF/плагина; расширять отправку с карточек на другие допустимые игровые активы. CS2, Dota 2, TF2, Rust и будущие игры подключать через игровые adapters/capabilities, не считать наличие parser/snapshot уже готовой доставкой.
- Preview, резервирование, распределение между ботами, отправка, журнал offer и сверка должны работать с любым поддержанным типом актива. Перед отправкой сверять фактический тип и asset ID; неподдерживаемые ASF/Steam типы явно отклонять до резервирования/отправки.
- Один заказ может включать разные типы активов и несколько delivery legs. Для каждого сохранять точные asset ID, бота, игру и offer ID. Сводный статус родительского заказа рассчитывается из состояний всех обязательных legs.
- Текущая поддержка инвентарей и доставка карточек не должны выдаваться за уже реализованную универсальную выдачу: это отдельная будущая доработка этапов C.5–C.6.

### 3.14 Таблица заказов и атрибуты сделки

Обновить отображение вкладки «Заказы» и модель полей без потери текущих данных:
- **ID заказа:** для заказа с площадки брать внешний ID именно сделки из её URL. Для Playerok использовать deal ID со страницы сделки `/deal/<ID>`, а не chat ID и не ID объявления. Нажатие на ID открывает встроенный браузер GameDelivery на соответствующей странице конкретной сделки. Для других площадок использовать их собственный внешний ID и URL через адаптер. Для ручного заказа сохранять внутренний ID и открывать карточку заказа внутри программы.
- **Источник:** название площадки-источника (`Playerok`, другая подключённая площадка и т. п.); если заказ создан вручную в GameDelivery — `Ручной заказ`.
- **Товар:** заменить заголовок/поле `Товар/активы` на `Товар`. Для сделки с площадки показывать название объявления/listing, по которому поступил заказ. Для ручной отправки показывать `Ручная отправка`. Список конкретных активов и их asset ID остаётся в деталях заказа, не вместо названия товара в основной таблице.
- **Цена:** добавить отдельный столбец `Цена` непосредственно перед столбцом даты заказа. На перспективу в конфигурации объявления хранить цену, валюту, комиссию площадки/платёжные сборы и расчётную сумму продавца; заказ сохраняет snapshot значений на момент покупки. Не подменять цену количеством предметов.
- **Дата:** текущий столбец `Обновлено` должен отображать дату и время создания/поступления заказа, а не время последнего изменения. Переименовать его в `Дата заказа`. Не добавлять отдельную колонку последнего изменения без отдельного решения.
- **Ширина:** каждый столбец должен полностью показывать содержимое без принудительного многоточия/обрезания. Ширина должна подстраиваться под содержимое; если все колонки физически не помещаются на экран, использовать горизонтальную прокрутку/перенос текста, а не скрывать часть значения. Длинный текст должен оставаться доступен полностью.

### 3.15 Сообщение в Steam trade offer

При создании trade offer GameDelivery должен отправлять предложение с пустым текстом сообщения. Убрать из сообщения строку вида `sent by ArchiSteamFarm-modded/6.3.11.7 (GameDelivery order id ...)` и любые другие автоматически подставляемые пояснения. ID заказа, технические данные и связь с offer хранить внутри GameDelivery/локального журнала, не помещать в публичное сообщение покупателю. До изменения проверить, где именно ASF/plugin задаёт `message` при создании offer, и обеспечить пустое значение на фактическом runtime path; одной правки UI недостаточно. Добавить тест, подтверждающий пустое сообщение в аргументе создания offer.

### 3.16 Товары без Steam-обмена и сценарии помощи по объявлениям

Не каждый товар требует Steam-бота или торгового предложения. В конфигурации объявления/товара предусмотреть выбираемый тип исполнения и capability:
- Steam trade с отправкой предметов через ASF;
- цифровой товар/ключ/код;
- файл;
- услуга/ручное выполнение;
- иные будущие способы доставки через подключаемые обработчики.

Для объявлений, которым Steam не нужен, не требовать Steam bot, trade URL или резервирование Steam asset ID. Для каждого такого объявления предусмотреть отдельные настраиваемые автосообщения и сценарии помощи покупателю: триггер (событие/ошибка), диагностические условия, готовый скрипт/последовательность разрешённых действий, текст ответа, лимит повторов и переход к оператору. Сценарии могут различаться для каждого объявления и/или группы объявлений. Неизвестная ошибка, недостаток данных или неоднозначный результат должны переводиться к оператору, а не запускать опасный универсальный скрипт. Редактор сценариев, версии, тестовый режим и журнал выполнения согласуются с общими правилами разделов 3.4–3.5.

### 3.17 Расширяемость, корректировка и добавление функций

Проект должен позволять в дальнейшем менять, исправлять и добавлять функции без переписывания системы с нуля и без поломки уже работающих сценариев. Для этого:
- статусы, команды, способы доставки, типы товаров, площадки, игровые инвентари, шаблоны и сценарии должны подключаться через явные версии контрактов/реестры;
- пользовательские настройки конкретного объявления/товара должны иметь версии и неизменяемый snapshot в каждом уже созданном заказе;
- новые поля SQLite вводить миграциями с сохранением существующих заказов, резервов и истории;
- скрипты и сценарии снабжать версиями, проверкой, тестовым запуском, журналом и безопасным откатом; не выдавать сценариям неограниченный доступ к секретам, базе или произвольным операциям;
- для каждого нового статуса/команды/типа доставки задавать допустимые переходы, разрешённые действия и fallback на ручную обработку;
- существующий рабочий функционал сохранять; изменения проводить малыми совместимыми шагами с тестами и регрессией.

## 5. Текущие решения пользователя (зафиксировано 2026-11-06)

1. Архитектура — **модульный монолит**.
2. Сообщения покупателям — **автоматизация с настройками и возможностью ручного подтверждения**.
3. Playerok и другие площадки — постепенное расширение; сначала объявления и сообщения, затем остальные операции.
4. Вход и управление каждой площадкой — через встроенный браузер.
5. Для площадок нужен редактор сценариев/функций; визуальный конструктор и расширяемые пользовательские скрипты предусмотрены как направление.
6. В системе доставки обязательно учитывать не только цифровые ключи/файлы/услуги, но и **Steam Trading Cards**, а также **предметы из игр** (включая будущую поддержку CS2).
7. Не забывать уже реализованную функциональность ASF, Steam-инвентаря, резерваций, карточек, плагина и существующего Playerok read-only импорта.
8. Перед каждой задачей сверяться с общим планом и этим файлом.
9. Не перескакивать между этапами без разрешения пользователя.
10. Если требование неясно — сначала исследовать проект и задачи, затем спросить.
11. Для Playerok не считать новые чаты или unread-счётчик новыми заказами: уникальность продажи определяется отдельным deal ID, а chat ID используется для связи с перепиской.
12. Для каждого объявления задавать количество предметов за одну покупку и привязки разрешённых предметов/ботов; заказ фиксирует snapshot конфигурации при покупке.
13. Общий запас предметов считается по всем ботам. Один заказ разрешено распределять между несколькими ботами и несколькими Steam-трейдами; физический asset ID глобально резервируется только один раз.
14. Telegram Bot должен поддерживать настраиваемые события, прокси, отдельные тесты подключения/сообщения и ответы оператора в нужный чат Playerok при строгой привязке к исходной сделке и проверке прав.
15. В инвентаре сохранить карточный режим и добавить компактный список с иконкой, названием и агрегированными количествами всего/передаваемого/непередаваемого; предметы с trade ban/unknown не резервировать, а countdown показывать только при достоверном времени разблокировки и подтверждать доступность свежим ASF snapshot.
16. После отправки Steam offer отслеживать его конечный статус: `Sent - ожидание покупателя` → `Принят покупателем` или `Отклонен покупателем`; отклонение обязательно уведомляет Telegram. Будущая кнопка «Выполнен заказ» на площадке запускается только после полного подтверждённого принятия всех обязательных offers.
17. При скрытом инвентаре покупателя отправлять инструкцию и ждать `!настроил приватность`; команда может запустить безопасную повторную попытку только после проверки buyer identity, order state, Steam offer history, reservations, exact asset IDs и idempotency key. При ограничении обменов отправлять покупателю сообщение и Telegram-уведомление, текущее решение — только ручное.
18. В заказах поддержать выбор и отправку предметов из любых подключённых игр, не ограничиваясь Steam Trading Cards; сохранить существующую карточную логику. Подготовить универсальный каталог статусов и место для будущих статусов.

Поэтому `sendDispatchStarted == false` сам по себе не доказывает, что отсутствие метода было непосредственно перед `SendTradeOffer`, и не позволяет объявить точную причину.

### 2026-11-07 — Playerok: lifecycle PAID → SENT → CONFIRMED и открытые вопросы интеграции

**Профиль для отслеживания:** `FANFIRIEL` (профиль/slug Playerok). Значение должно быть конфигурируемым; не зашивать его в код как неизменяемую константу.

**Подтверждённая пользователем семантика вкладок продаж:**
- `PAID` — оплаченные заказы, которые остаются в этом состоянии, пока продавец не выполнил заказ и не нажал на Playerok «Выполнил заказ». Наличие заказа в PAID означает необходимость обнаружить заказ и подготовить/выполнить выдачу, но не является подтверждением доставки.
- `SENT` — заказы, для которых продавец уже выполнил заказ и нажал «Выполнил заказ». Далее заказ ожидает подтверждения покупателем либо автоматического подтверждения площадкой через 7 дней. SENT не означает, что покупатель подтвердил получение или что заказ окончательно завершён.
- `CONFIRMED` — завершённые заказы; покупатель подтвердил получение либо площадка выполнила автоматическое подтверждение. Это терминальное подтверждённое состояние площадки.

Страницы профиля FANFIRIEL:
- PAID: https://playerok.com/profile/FANFIRIEL/sales?status=paid
- SENT: https://playerok.com/profile/FANFIRIEL/sales?status=sent
- CONFIRMED: https://playerok.com/profile/FANFIRIEL/sales?status=confirmed

**Обязательная модель переходов:** `PAID → SENT → CONFIRMED`.
1. В PAID GameDelivery обнаруживает заказ, сопоставляет его с внутренней сделкой/объявлением и выполняет подготовку и выдачу.
2. Переводить заказ в SENT (нажимать «Выполнил заказ» на Playerok) разрешено только после успешного завершения всех обязательных `DeliveryLeg` этого заказа. Если хотя бы один обязательный этап неуспешен, неизвестен или не завершён — действие недопустимо.
3. После перехода в SENT GameDelivery только отслеживает состояние и ожидает подтверждения. Нельзя повторно выполнять выдачу только потому, что заказ продолжает находиться в SENT.
4. В CONFIRMED фиксируется подтверждение покупателем или автоматическое подтверждение Playerok по истечении 7 дней. Не подменять это состояние локальным фактом отправки товара.
5. Сохранять в GameDelivery историю наблюдаемых статусов и переходов с временными отметками, источником наблюдения и связанными внутренними идентификаторами. Различать статус площадки и внутреннее состояние выполнения доставки.
6. Не считать наличие заказа в PAID доказательством отправки; не считать SENT доказательством принятия/подтверждения покупателем.

**Ограничения исследования и реализации:**
- Не предполагать наличие или доступность API для смены статуса Playerok. Сначала исследовать фактический интерфейс Playerok и доступный механизм нажатия «Выполнил заказ»; отдельно оценить возможность и границы встроенных browser scripts.
- До исследования не реализовывать выдуманные API-вызовы и не автоматизировать нажатие без надёжного подтверждения успешного завершения обязательных DeliveryLeg.
- Обработать неизвестный результат внешнего действия безопасно: сначала перечитать/сверить состояние Playerok, не повторять выдачу и не нажимать действие повторно вслепую.
- Сопоставление сделки и заказа должно использовать корректные идентификаторы Playerok; не смешивать `deal_id`, `chat_id` и `listing_id`.

Нельзя выводить количество товара из денежной суммы.

**Проблема 3 — резервирование и доставка не составляют единую транзакционную систему.** Резервирование ресурса, создание записи заказа и запись состава заказа выполняются раздельно. В текущей модели недостаточно истории резервирования и освобождения резервов. Также `PRAGMA foreign_keys=ON` не гарантирован для каждого SQLite connection. Необходимо обеспечить атомарность, трассируемость и проверку внешних ключей для каждого соединения.

**Проблема 4 — результат Steam-отправки хранится в двух местах.** SQLite приложения и `sent_offers.json` ASF-плагина — независимые хранилища состояния. Нужен единый механизм reconciliation, связывающий локальную попытку, внешний offer ID и наблюдаемое состояние предложения после перезапуска или сбоя.

Эти четыре проблемы определяют порядок последующих этапов: сначала согласовать доменную модель, затем построить учёт и только после этого подключать универсальную доставку и новые категории товаров.

#### 4. Целевая доменная модель и ключевые правила

| Сущность | Назначение |
|---|---|
| `Listing` | Объявление на площадке |
| `ConfigVersion` | Неизменяемая версия настроек объявления, используемая для конкретной покупки |
| `Deal` | Конкретная покупка/сделка на площадке |
| `Order` | Родительский внутренний заказ |
| `OrderLine` | Отдельная позиция товара, тип и количество |
| `DeliveryLeg` | Отдельная обязательная или необязательная часть доставки |
| `DeliveryAttempt` | Конкретная попытка исполнения DeliveryLeg |
| `ResourceReservation` | Резерв конкретного ресурса/актива/кода под заказ |

Один заказ может включать, например, десять карточек с трёх ботов и несколько отдельных Steam trade offers. Каждый offer должен иметь собственный внешний ID, попытки и историю состояния; заказ должен иметь общий вычисляемый статус по всем обязательным DeliveryLeg. Изменение объявления после покупки не должно менять количество, цену/параметры или состав уже оплаченного заказа: Order должен ссылаться на зафиксированный ConfigVersion/snapshot.

**Обязательные правила C.3:**
- атомарная резервация ресурса и состава заказа;
- запрет двойного использования одного Asset ID;
- журнал резервирования, истечения, освобождения и потребления ресурсов;
- согласованный пересчёт `delivered / reserved / remaining`;
- безопасные аддитивные миграции с backup и проверяемым rollback;
- `PRAGMA foreign_keys=ON` при создании каждого SQLite connection;
- конкурентные тесты на одновременное резервирование одного и того же ресурса;
- сохранение и reconciliation внешних идентификаторов Steam offers.

#### 5. Общий контракт исполнения доставки и безопасность неизвестного результата

Целевой жизненный цикл обработчика:

`preview → reserve → prepare → execute → reconcile`

Обработчик должен уметь сообщить о возможностях/ограничениях (capability check), показать предварительный план, зарезервировать ресурсы, подготовить операцию, выполнить внешнее действие и затем сверить фактический результат. Повторные события не должны повторно выдавать один и тот же ресурс. Если результат внешнего действия неизвестен (таймаут, падение процесса, потеря ответа), система не должна автоматически трактовать его как «не выполнено» и повторять операцию. Сначала необходимо выполнить reconciliation по внешнему ID/источнику. Неизвестный результат остаётся отдельным безопасным состоянием до выяснения факта.

## 2026-11-07 — C.2: согласована логика подбора обычных Steam Trading Cards по значкам покупателя

**Статус:** пользователь подтвердил бизнес-правила подбора и приоритетов. Это уточнение доменной спецификации C.2, а не завершение всего этапа C.2. Технические источники данных и реализация пока не проверены. Код, пользовательская БД, миграции и UI в рамках этой записи не менялись.

### 1. Только обычные карточки

- Используются исключительно обычные Steam Trading Cards.
- Foil cards и фольгированные значки полностью исключены из каталога, расчётов, доступного запаса и выдачи.
- Состав набора и количество различных карточек в нём программа должна определять автоматически по данным значков/наборов Steam на профилях собственных ASF-ботов. Нельзя требовать ручного заполнения состава для каждой игры.
- Точный способ получения состава набора и устойчивый идентификатор карточки между ботами и покупателем требуется подтвердить на реальных данных; не предполагать неподтверждённый API.

### 2. Расчёт прогресса покупателя

Для каждой игры программа проверяет:
- текущий уровень обычного значка покупателя (0–5);
- количество полных обычных наборов этой игры в инвентаре покупателя.

Частичные наборы не учитываются. Если набор состоит из N разных карточек, число полных наборов в инвентаре определяется как минимум количества экземпляров каждого из N требуемых типов карточек.

Формула недостающего количества для достижения 5-го уровня:

`required_sets = max(0, 5 - badge_level - buyer_complete_sets)`

Примеры:
- уровень 0, полных наборов 0 → нужно 5;
- уровень 3, полных наборов 0 → нужно 2;
- уровень 3, полных наборов 2 → нужно 0;
- уровень 0, полных наборов 5 → нужно 0;
- уровень 5 → нужно 0 независимо от инвентаря.

Имеющиеся частичные наборы не уменьшают требуемое количество.

### 3. Приоритет распределения заказа

- Количество из конфигурации оплаченного объявления — строгое обязательство в полных наборах. Заказ на 10 наборов должен быть распределён ровно на 10, без недовыдачи и перевыдачи.
- Первый приоритет алгоритма — максимизировать количество значков, которые можно довести до 5-го уровня в рамках заказа и фактического запаса. Например, если заказ на 10 наборов и две игры требуют по 5 наборов, предпочтительное распределение — 5 + 5, чтобы завершить два значка.
- После максимизации числа завершённых значков остаток оплаченного количества распределяется по другим подходящим играм, даже если оставшиеся наборы не доведут следующий значок до 5-го уровня.
- Игры выбираются программой автоматически с учётом badge progress, полного состава наборов и доступного запаса ботов. Детерминированные tie-break правила для равноценных комбинаций будут уточнены до реализации и покрыты тестами.
- Если нельзя подобрать ровно всё оплаченное количество, до начала внешних отправок не отправлять ни одного offer. Частичную выдачу из-за нехватки карточек запрещено начинать.

### 4. Единый пул ботов и многоботовые наборы

- Инвентарь всех разрешённых ASF-ботов образует единый логический пул.
- Один полный набор может состоять из карточек нескольких ботов. Например, часть разных карточек набора принадлежит боту A, остальные — боту B; для покупателя это один набор.
- Каждый физический актив сохраняет точную привязку к `(bot_name, asset_id)` и глобально резервируется только один раз.
- При необходимости создаются отдельные DeliveryLeg/Steam trade offers от разных ботов. Родительский заказ завершён только после достижения согласованного подтверждённого результата всеми обязательными legs.

### 5. Недостаток запаса и уведомления

Если до первого внешнего действия невозможно сформировать полный оплаченный заказ:
- не отправлять ни одного Steam offer;
- сообщить покупателю: **«Подходящих карт для вашего аккаунта нет, ожидаем продавца в чате для решения проблемы»**;
- отправить оператору Telegram-уведомление с контекстом сделки, причиной и недостающим составом/количеством;
- сохранить заказ в состоянии ожидания решения продавца.

Telegram — дополнительный канал уведомлений; его недоступность не должна терять заказ или приводить к повторной выдаче.

Важное техническое ограничение: если заказ уже начал исполняться несколькими внешними trade legs и одна leg успешно отправлена, а последующая завершилась ошибкой/unknown, внешнюю отправку первой leg нельзя откатить. Такой случай фиксируется как частичный/неизвестный внешний результат, требует reconciliation и уведомления оператора; повтор уже отправленной leg запрещён. Это не разрешает намеренно начинать частичную выдачу при недостатке запаса на этапе предварительного подбора.

### 6. Приватность покупателя

- Если профиль, значки или инвентарь недоступны из-за настроек приватности, подбор и отправка блокируются.
- Используется один общий сценарий: покупателю отправляется инструкция открыть все необходимые настройки приватности Steam (профиль, сведения об играх/значках и инвентарь).
- После команды покупателя `!настроил приватность` GameDelivery повторно проверяет доступность данных и продолжает только после успешной проверки.
- Команда должна быть привязана к конкретной сделке/покупателю, быть идемпотентной и не обходить блокировку повторной отправки или unknown outcome.

### 7. Сущности и открытые технические проверки C.2

Подтверждённая целевая цепочка:
`Listing → ConfigVersion → Deal → Order → OrderLine → DeliveryLeg → DeliveryAttempt`, с отдельными `ResourceReservation` для точных asset ID.

До закрытия C.2 требуется доказать:
1. Как получать состав обычного набора и число карточек из значков/наборов собственных ботов.
2. Как устойчиво сопоставлять типы карточек между ботами и профилем покупателя.
3. Как надёжно получать уровень значка и полный инвентарь покупателя.
4. Как обнаруживать приватность и проверять, что общая инструкция устранила ограничение.
5. Как безопасно отправлять покупателю сообщение и привязать `!настроил приватность` к сделке.
6. Детерминированные tie-break правила для равноценных вариантов подбора.
7. Regression/contract tests для уровней 0–5, полных и частичных наборов, приоритета завершения нескольких значков, остатка, смешанных ботов, дефицита одной карточки, privacy retry, нескольких trade legs и unknown outcome.

**Следующий шаг:** завершить техническое проектирование C.2 и подтвердить источники данных на существующих Steam/ASF механизмах. До этого не менять пользовательскую БД, не запускать миграции и не переписывать большой UI. После утверждения C.2 отдельно перейти к C.3.

## 2026-11-07 — C.2: подтверждён ASF-native путь к Steam Community и инвентарю получателя

**Статус:** статический контракт подтверждён по исходникам официального ASF 6.3.11.7, на который закреплена сборка GameDelivery ASF plugin. Это существенно сужает техническую неопределённость C.2, но live-запросы Steam через пользовательскую ASF-сессию ещё не выполнены. Код GameDelivery, пользовательская БД, миграции и UI не менялись.

**Проверенная версия ASF:** workflow `.github/workflows/asf-plugin.yml` скачивает и проверяет официальный ASF 6.3.11.7; в официальном теге `6.3.11.7` `Directory.Build.props` содержит `<Version>6.3.11.7</Version>`. Проверялись именно исходники этого тега, а не только текущая ветка ASF.

**Подтверждённые публичные API ASF 6.3.11.7:**

1. `Bot.ArchiWebHandler` — публичное свойство класса `Bot`.
2. `ArchiWebHandler.UrlGetToJsonObjectWithSession<T>(Uri ...)` и `UrlGetToHtmlDocumentWithSession(Uri ...)` — публичные методы. Они используют web session ASF; обработчик поддерживает проверку/обновление сессии и внутреннее ограничение частоты запросов.
3. `ArchiWebHandler.GetInventoryAsync(ulong steamID = 0, uint appID = 753, ulong contextID = 6, ...)` — публичный асинхронный поток активов. При `steamID=0` используется собственный аккаунт бота; ненулевой SteamID принимается, если это individual account. Метод запрашивает Steam Community inventory по `/inventory/{steamID}/{appID}/{contextID}`, обрабатывает страницы `more_items/last_assetid`, дедуплицирует asset ID, связывает descriptions по `classid+instanceid`, применяет ASF inventory limiter и выбрасывает ошибку при неуспешном ответе. Следовательно, ASF-native механизм для чтения публичного инвентаря получателя существует; текущий GameDelivery его пока не вызывает.
4. ASF `Asset`/ `InventoryDescription` предоставляют `AssetID`, `Amount`, `RealAppID`, `Type`, `Tradable`, `MarketHashName`, `ClassID` и `InstanceID`. Это позволяет считать карточки покупателя по устойчивому market hash и отдельно проверять обычный/фольгированный тип. Для подсчёта уже имеющихся у покупателя полных наборов нельзя отбрасывать карточки только потому, что они непередаваемые: передаваемость нужна для нашего донорского запаса, а не для факта владения покупателя.
5. Внутренний ASF `GetGameCardsPage(appID)` использует `/my/gamecards/{appid}?l=english`, а `GetCardCountForGame` считает элементы `badge_card_set_cards`. Сам `GetGameCardsPage` помечен internal, но публичный `UrlGetToHtmlDocumentWithSession` позволяет плагину запросить страницу через ASF-сессию. Внутренняя реализация ASF подтверждает существование страницы и способ подсчёта количества, но не является готовым публичным API полного каталога карточек.

**Кандидат для состава набора и уровня значка:**

- Reverse-engineered описание Steam Community endpoint `GET /profiles/{steamid}/ajaxgetbadgeinfo/{appid}` указывает на JSON `eresult`, `badgedata.level`, `badgedata.maxlevel`, `badgedata.border` и `badgedata.rgCards[]`; карточка содержит `markethash` и `owned`. В примере для собственного профиля используется `/my/ajaxgetbadgeinfo/{appid}`. Документация помечена authenticated и последний раз обновлялась 24.02.2022; это не официальный и не гарантированный Steam production contract. Источник: https://github-wiki-see.page/m/Revadike/InternalSteamWebAPI/wiki/Get-Badge-Info
- Предварительный вариант: вызывать endpoint через `Bot.ArchiWebHandler.UrlGetToJsonObjectWithSession<JsonElement>`, для собственных ботов — `/my/ajaxgetbadgeinfo/{appid}`, для покупателя — `/profiles/{steamid}/ajaxgetbadgeinfo/{appid}`. В production допускать ответ только после live-проверки и строгой валидации `eresult`, appid, border=0, level 0–5, maxlevel=5 и полного уникального списка `rgCards`.
- Поле `owned` пока не использовать как источник истины. Число полных наборов покупателя считать по фактическому инвентарю, полученному через ASF `GetInventoryAsync`, сопоставляя каждую карточку с составом набора.
- Официальная Steam FAQ подтверждает, что Badges in Progress показывает имеющиеся и недостающие карточки, а набор для обычного игрового значка можно изготовить не более пяти раз: https://steamcommunity.com/tradingcards/faq/Steam

**Важное уточнение к предыдущему аудиту:** утверждение об отсутствии buyer-inventory provider относилось к существующему GameDelivery-коду/ASF IPC wrapper. Оно не означает, что сам ASF не умеет читать инвентарь другого пользователя: публичный `ArchiWebHandler.GetInventoryAsync(steamID, 753, 6)` существует в точной версии 6.3.11.7. Готовой интеграции этого метода в GameDelivery всё ещё нет.

**Следствия для будущего контракта C.2 (без реализации):**

- Steam-запросы остаются внутри ASF plugin; приложение не получает Steam cookies/access tokens и не вызывает Steam Web API напрямую.
